# 연구 노트 — 과제 3 / 1단계

# 1단계 : 표적 구조체 정의

## 1-1. 목적

표적 하나를 컴퓨터가 다루려면 숫자가 여러 개 필요하다.
어디에 있는지(위도·경도·고도), 얼마나 빠른지(속도), 어느 쪽을 보고 있는지(자세각),
언제 어떻게 도는지(기동 정보)...

표적이 10개면 이런 숫자가 수백 개가 된다. 변수를 따로따로 만들면 관리가 불가능하다.
그래서 **관련된 값을 하나로 묶는 그릇**이 필요하다. C 언어에서는 이것을 **구조체(struct)** 라고 한다.

이번 단계의 목적은 과제 명세가 요구하는 표적 정보를 담을 구조체를 설계하는 것이다.
아직 계산은 하지 않는다. 그릇만 만든다.

결과물 : `TargetSimCore/include/TargetSim.h`

## 1-2. 알아야 할 기본 개념

### (1) 위도 · 경도 · 고도 (LLA)

지구 위의 한 점을 가리키는 방법이다.

- **위도(Latitude)** : 적도에서 남북으로 얼마나 떨어졌는가. −90°(남극) ~ +90°(북극)
- **경도(Longitude)** : 영국 그리니치를 지나는 선에서 동서로 얼마나 떨어졌는가. −180° ~ +180°
- **고도(Altitude)** : 지구 표면에서 위로 얼마나 떨어졌는가. 단위 m

여기서 "지구 표면"은 실제 산과 바다가 아니라 **수학적으로 정의한 매끈한 지구 모양**을 말한다.
지구는 완전한 공(구)이 아니라 **적도가 부풀고 극이 납작한 타원체**다.

- 적도 반지름 a = 6,378,137 m
- 극 반지름   b = 6,356,752 m
- 차이 약 21 km

이 모양을 정의한 국제 표준이 **WGS84** 이고, GPS 가 쓰는 것과 같은 기준이다.

### (2) 자세각 (Roll · Pitch · Yaw)

"어디에 있는가" 와 별개로 "어느 쪽을 보고 어떻게 기울어져 있는가" 를 나타낸다.

비행기나 배 자신을 기준으로 한 축을 **동체 좌표계(Body)** 라고 하고, 이렇게 잡는다.

- x 축 : 앞 (기수 방향)
- y 축 : 오른쪽 (우현)
- z 축 : 아래

이 세 축을 중심으로 도는 것이 각각 자세각이다.

| 이름 | 회전축 | 쉬운 비유 |
|---|---|---|
| Roll (롤) | x 축 (앞) | 옆으로 기울이기 (통나무 구르기) |
| Pitch (피치) | y 축 (오른쪽) | 기수 들기 / 내리기 (시소) |
| Yaw (요) | z 축 (아래) | 좌우로 방향 틀기 (자동차 핸들) |

Yaw 만 보면 방향이 바로 나온다. 0° 가 북쪽이고 시계 방향으로 커진다.

```
Yaw   0° = 북
Yaw  90° = 동
Yaw 180° = 남
Yaw 270° = 서
```

과제의 대함 표적은 Yaw 270° → **서쪽으로 간다**
과제의 대공 표적은 Yaw 180° → **남쪽으로 간다**

### (3) 속도를 왜 숫자 하나로 받는가

속도는 원래 방향과 크기를 함께 가진 **벡터**다. 3차원이면 (Vx, Vy, Vz) 세 개가 필요하다.

그런데 비행기나 배는 **자기가 향한 방향으로 간다.** 방향은 이미 자세각이 알려준다.
그러니 **크기 하나만** 받으면 충분하다. 이것을 명세에서 **V_heading** 이라고 부른다.

동체 좌표계에서 속도 벡터는 이렇게 된다.

```
V_body = ( V_heading , 0 , 0 )
```

x 축(앞)으로만 값이 있고 옆(y)과 아래(z)는 0 이다. 즉 "옆으로 미끄러지거나 아래로 처지지 않는다".

### (4) 기동(Maneuver) 과 G

직진만 하면 시뮬레이션이 단조롭다. 중간에 도는 동작을 **기동** 이라고 한다.
명세는 기동을 네 가지 정보로 표현하라고 했다.

| 정보 | 뜻 |
|---|---|
| Gravity Value | 얼마나 급하게 도는가 (중력가속도의 몇 배) |
| TurnType | 어느 축으로 도는가 (0 안 돔 / 1 Roll / 2 Yaw / 3 Pitch) |
| StartTime | 언제부터 |
| EndTime | 언제까지 |

**G 가 무엇인가**

놀이기구에서 몸이 좌석에 눌리는 느낌이 곧 가속도다.
지구 중력과 같은 세기를 **1 G** 라고 하고, 그 값은

```
g = 9.80665 m/s²
```

3 G 라면 몸무게의 3 배로 눌리는 느낌이다.
비행기가 원을 그리며 돌 때 바깥으로 쏠리는 힘의 세기를 이렇게 G 로 표현한다.
그래서 **Gravity Value = 얼마나 급하게 도는가** 를 뜻한다. 값이 클수록 작은 원을 빠르게 돈다.

| 명세가 요구한 것 | 어떻게 구현했나 |
|---|---|

| 표적별 기동 횟수 설정 가능 (최대 30) | `TGT_MAX_MANEUVER_NUM 30`, 실제 개수는 `nManeuverNum` |

```
ST_TargetState     한 시각의 상태      (시각, ECEF 위치, ECEF 속도, LLA, 자세각)
```

## 1-4. 명세에 없어서 직접 판단한 3 가지

명세가 정해주지 않은 부분이 세 군데 있었다. 각각 아래와 같이 결정했다.

### (1) 선회 방향을 어떻게 표현할 것인가

**문제** : 명세의 Gravity Value 는 "얼마나 세게" 만 준다. 오른쪽으로 도는지 왼쪽으로 도는지가 없다.

**결정** : **Gravity Value 의 부호(+, −)로 방향을 표현한다.**

**이유** : 명세가 기동 정보를 4 개로 못박았다. 방향 필드를 새로 만들면 명세를 벗어난다.
부호는 어차피 안 쓰고 있던 정보이므로 필드를 늘리지 않고 해결할 수 있다.

**부호 약속** : 수학·공학의 표준인 **오른손 법칙** 을 따른다.
오른손 엄지를 회전축 방향으로 두면, 나머지 네 손가락이 감기는 방향이 (+) 다.

```
Roll  (+) 오른쪽으로 기울임   (−) 왼쪽으로 기울임
Pitch (+) 기수 들어올림       (−) 기수 내림
Yaw   (+) 오른쪽으로 선회     (−) 왼쪽으로 선회
```

### (2) Roll 기동은 궤적에 어떻게 반영되는가

**문제** : Yaw 로 돌면 진행 방향이 바뀐다. Pitch 로 돌면 오르내린다.
그런데 Roll 은 몸을 옆으로 기울이는 것이라, 그것만으로는 어디로 갈지 안 바뀐다.

**결정** : **TurnType 을 "어느 축을 돌리는가" 로 문자 그대로 해석한다.**
Roll 기동이면 roll 각만 바뀌고 궤적은 직진한다.

**검토했다가 버린 안** : 실제 비행기는 옆으로 기울이면(뱅크) 그 힘으로 선회한다(조화 선회).
이 방식을 쓰면 `선회율 = g · tan(뱅크각) / V` 가 된다.
하지만 그러려면 Gravity Value 를 "하중배수" 라는 다른 의미로 재해석해야 하고,
결과적으로 Yaw 타입과 하는 일이 똑같아져 타입을 나눈 의미가 없어진다. 그래서 배제했다.

### (3) 기동 구간이 겹치면 어떻게 하는가

**문제** : 한 표적에 기동을 30 개까지 넣을 수 있다.
누가 실수로 "0~30초 Yaw", "20~40초 Pitch" 처럼 겹치게 넣으면?

**결정** : **겹치면 오류로 처리한다.** 시간순으로 겹치지 않는 구간만 허용한다.
시뮬레이션을 시작하기 전에 입력 검증 단계에서 걸러낸다. (검증 함수는 2단계에서 구현)

**이유** : 겹침을 허용하면 두 축이 동시에 도는 복잡한 동작이 되어 결과 설명이 어려워진다.
과제는 궤적 모의 원리를 보이는 것이 목적이므로 단순하고 예측 가능한 쪽을 택했다.

## 1-5. 단위 규약

프로그램 전체에서 단위를 하나로 통일했다. 단위가 섞이면 반드시 사고가 난다.

| 양 | 단위 |
|---|---|
| 각도 (위도, 경도, 자세각) | **라디안 (rad)** |
| 길이 | m |
| 속도 | m/s |
| 시간 | s |
| Gravity Value | G 배수 (무단위) |

**왜 도(°) 가 아니라 라디안인가**

C 언어의 `sin()`, `cos()`, `atan2()` 같은 수학 함수는 전부 라디안을 받는다.
구조체에 도로 저장해 두면 함수를 부를 때마다 변환해야 하고, 한 번만 빠뜨려도 결과가 엉망이 된다.
그래서 **저장은 라디안, 사람에게 보여줄 때만 도로 바꾸는** 방식을 택했다.

**변환식**

```
라디안 = 도 × π / 180        (예:  90° × 3.14159 / 180 = 1.5708 rad)
도     = 라디안 × 180 / π     (예:  1 rad × 180 / 3.14159 = 57.2958°)
```

```
1 rad = 57.2958°
1°    = 0.01745329 rad
```

**Gravity Value 를 실제 가속도로 바꾸는 식**

```
실제 가속도 a = Gravity Value × g = Gravity Value × 9.80665   [m/s²]
```

## 1-6. 메모리 설계

### 왜 배열 크기를 미리 고정하는가

표적 개수를 실행 중에 늘렸다 줄였다 하려면 보통 `malloc()` 으로 메모리를 빌린다.
하지만 이 프로젝트는 **MISRA C 규칙을 따르기로 했고, 그 규칙은 동적 할당을 금지한다.**

이유는 이렇다.

- 메모리를 다 쓰고 반납하지 않으면 새는 것(메모리 누수)이고
- 빌리려다 실패하면 프로그램이 멈추며
- 언제 얼마나 걸릴지 예측이 안 된다

레이다 같은 실시간·안전 중요 시스템은 **미리 최대치만큼 잡아두고 실제 쓰는 개수만 따로 세는** 방식을 쓴다.
그래서 배열은 `[10]`, `[30]` 으로 고정하고 `nTargetNum`, `nManeuverNum` 으로 유효 개수를 관리한다.

### 실제 크기 (x64 기준 실측)

| 구조체 | 크기 | 계산 근거 |
|---|---|---|
| `ST_TargetManeuver` | 32 B | enum 4 + 패딩 4 + double 8 × 3 |
| `ST_TargetInit` | 1,024 B | LLA 24 + 자세각 24 + 속도 8 + 개수 8 + 기동 32 × 30 = 960 |
| `ST_PlatformInit` | 56 B | |
| `ST_SimConfig` | 10,320 B | 시간 16 + 플랫폼 56 + 개수 8 + 표적 1024 × 10 |
| `ST_TargetState` | 104 B | |

**패딩이란** : CPU 가 8 바이트 단위로 읽는 것이 빠르기 때문에, 컴파일러가 구조체 사이에 빈 공간을 끼워 넣어
주소를 맞춰 준다. 그래서 4 + 8 + 8 + 8 = 28 이 아니라 32 가 된다.

**주의할 점** : `ST_SimConfig` 가 약 10 KB 다.
함수 안에 지역 변수로 선언하면 스택(임시 메모리)을 많이 쓰므로,
UI 에서는 **클래스 멤버 변수로 보관** 하기로 했다.

60 초 / 0.1 초 = 600 스텝(기록은 t = 0 을 포함해 601 개)이고, 표적 2 개의 궤적을 전부 저장하면
`601 × 2 × 104 B ≈ 122 KB` 이다. 충분히 작다.

**이전에 기록한 내용 중 WGS84 상수 항목은 아래와 같이 정정한다.**

| # | 위치 | 내용 | 실질 영향 |

**정정 사유** : WGS84 이심률이 "절삭되어 m 단위 오차를 유발한다" 고 기록했으나,

_JH 버전은 이심률을 편평률 f 에서 직접 유도하여 두 상수가 어긋날 여지 자체를 없앴다.

```
f  = 1 / 298.257223563
b  = a × (1 − f)
e² = f × (2 − f)
e'² = e² / (1 − e²)
```
