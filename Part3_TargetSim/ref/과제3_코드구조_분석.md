# 1. 전체 조망

## 1.1 이 프로그램이 하는 일

플랫폼(함정) 하나와 표적 최대 10개를 지구 위에 배치하고, 각 표적에 최대 30개의 기동을
지정한 뒤, 정해진 시간 간격으로 전원의 위치·속도·자세를 갱신해 궤적을 만든다.
결과는 위도·경도·고도(LLA) 표와 CSV, 그리고 평면 궤적 그림으로 낸다.

물리적으로는 **한 문장**으로 요약된다.

```
표적은 항상 자기 기수(機首) 방향으로 일정한 속력 V 로 간다.
기동은 위치를 직접 건드리지 않고 "기수 방향" 만 돌린다.
```

이 한 문장이 자료구조와 적분 방식을 모두 결정한다. 3.4절과 5.6절이 그 이유다.

## 1.2 두 개의 프로젝트

```
TargetSim.sln
├── TargetSimCore   (C17, DLL)          계산 — Windows/MFC 를 전혀 모른다
└── TargetSimUI     (C++17, MFC 대화상자) 입력·출력 — 계산을 전혀 하지 않는다
```

| | TargetSimCore | TargetSimUI |
|---|---|---|
| 언어 | C17 (`LanguageStandard_C = stdc17`) | C++17 (`stdcpp17`), MFC 동적 링크 |
| 산출물 | `DynamicLibrary` (DLL) | `Application` (EXE) |
| 내보내기 | `TSCORE_API` = `__declspec(dllexport/import)` | — |
| 의존 | C 표준 라이브러리(`math.h`) 뿐 | Core + MFC + GDI+ |
| 각도 단위 | **라디안만** | 화면은 도(°), 경계에서 변환 |
| 오류 처리 | 반환 코드 (`EN_TgtStatus` 등) | 코드를 한국어 문구로 번역 |

**경계가 이렇게 그어진 이유** — 계산부가 UI 를 모르면
(a) 콘솔 하네스로 단독 검증할 수 있고,
(b) 다른 UI(웹, 콘솔, 다른 시뮬레이터)에 그대로 붙일 수 있으며,
(c) 명세가 요구한 "표적 구조체 정의"가 화면 사정에 오염되지 않는다.

실제로 `과제3_명세대조_정정기록.md` 의 모든 수치 검증은 UI 없이 Core 만 정적 링크한
임시 하네스로 측정했다. 이 문서 9절의 재현도 같은 방식이다.

빌드 연결은 `TargetSimUI.vcxproj:142` 의 `<ProjectReference>` 와
`TargetSimUI.vcxproj:61` 의 `AdditionalIncludeDirectories = $(SolutionDir)TargetSimCore\include` 뿐이다.
UI 는 Core 의 `include/` 만 본다. Core 의 `src/` 는 보지 않는다.

## 1.5 빌드 구성

| 항목 | Core | UI |
|---|---|---|
| 플랫폼 | x64 (Win32 구성 없음) | x64 |
| 경고 수준 | `Level4` | 기본 |
| 전처리기 | `TARGETSIMCORE_EXPORTS`, `_USRDLL` | `_WINDOWS` |
| 포함 경로 | `$(ProjectDir)include` | `$(ProjectDir);$(SolutionDir)TargetSimCore\include` |
| MFC | — | `Dynamic` |

`TargetSimCoreApi.h` 의 3분기가 이 구성을 받는다.

```c
#if defined(_WIN32) && !defined(TARGETSIMCORE_STATIC)
    #ifdef TARGETSIMCORE_EXPORTS
        #define TSCORE_API  __declspec(dllexport)   // Core 를 빌드할 때
    #else
        #define TSCORE_API  __declspec(dllimport)   // UI 가 Core 를 쓸 때
    #endif
#else
    #define TSCORE_API                              // 비Windows 또는 정적 링크
#endif
```

`TARGETSIMCORE_STATIC` 를 정의하면 `__declspec` 이 사라지므로, **Core 를 그대로
gcc/clang 으로 컴파일해 콘솔 하네스에 정적 링크할 수 있다.** 9절의 재현이 이 경로다.

# 2. 읽기 전에 — 코딩 규약이 코드 모양을 어떻게 정하는가

이 코드는 `ref/codingRule.md` 와 MISRA C 스타일을 따른다. 규약을 모르면
"왜 이렇게 장황한가" 로 읽히고, 알면 "왜 이 모양일 수밖에 없는가" 로 읽힌다.
**규약은 코드 스타일이 아니라 코드 구조를 만든다.**

## 2.1 이름 규칙

| 접두사 | 뜻 | 예 |
|---|---|---|
| `ST_` / `st_` | 구조체 타입 / 구조체 변수 | `ST_SimConfig` / `st_Config` |
| `EN_` / `en` | 열거형 타입 / 열거형 변수 | `EN_TgtStatus` / `enStatus` |
| `f_` | 함수 | `f_Tgt_StepSim` |
| `pt_` | 포인터 변수 | `pt_Element`, `pt_Buf` |
| `n` | 개수·인덱스 | `nTargetNum`, `nStep` |
| `s_` | 정적 전역 | `s_SpecTarget`, `s_PlaySpeed` |
| `is` | 불리언 의미의 `INT32` | `isOk`, `isPlaying`, `isResultStale` |
| 대문자 | `#define` | `TGT_MAX_TARGET_NUM` |

함수 이름의 두 번째 토큰이 **모듈 구분**이다.
`f_Tgt_*`(엔진) · `f_Coord_*`(좌표 기본) · `f_Trans_*`(좌표 변환) · `f_Mat_*`(행렬) ·
`f_Num_*`(숫자 문자열) · `f_Ui_*`(화면 보조) · `f_Scn_*`(시나리오 내부) · `f_Plot_*`(그림 내부).
**이름만 보고 어느 파일에 있는지 알 수 있다.**

## 2.2 기본형 금지

`int`, `double`, `bool` 을 직접 쓰지 않고 `Define_JH.h:16-37` 의 typedef 를 쓴다.

```c
typedef signed int      INT32;
typedef double          FLOAT64;
typedef char            CHAR;
typedef void            VOID;
```

`VOID` 만 `#ifndef` 로 감싼 이유는 Windows SDK 가 먼저 매크로로 정의하는 경우가
있기 때문이다 (`Define_JH.h:11-13`). UI 쪽에서도 이 규칙이 지켜져서,
MFC 재정의 함수의 반환형까지 `VOID`/`INT32` 로 적혀 있다.

## 2.3 함수당 return 한 개

이것이 코드 모양을 가장 크게 바꾼다. 중간에 빠져나갈 수 없으므로
**상태 변수를 하나 두고 조건을 체인으로 잇는다.**

```c
// TargetSim_JH.c:294  f_Tgt_Propagate 의 전형적인 모양
enCoord = f_Tgt_GetVelEcef(&st_VelStart, ...);

if (enCoord == COORD_OK) { enCoord = f_Coord_VecScale(&st_Delta, &st_VelStart, halfStep); }
if (enCoord == COORD_OK) { enCoord = f_Coord_VecAdd(&st_PosMid, &st_State->st_PosEcef, &st_Delta); }
if (enCoord == COORD_OK) { enCoord = f_Trans_Ecef_To_Lla(&st_LlaMid, &st_PosMid); }
/* ... */
if (enCoord == COORD_OK) { *st_State = st_Next; enStatus = TGT_OK; }
else                     { enStatus  = TGT_ERR_COORD; }

return enStatus;                                    // ← 유일한 return
```

한 번 실패하면 이후 블록이 전부 건너뛰어지고 마지막에 한 번 판정한다.
**이 패턴을 알면 Core 의 거의 모든 함수를 한눈에 읽을 수 있다.**

같은 이유로 `for` 루프 안에서도 `break` 대신 조건을 쓴다.

```c
// TargetSim_JH.c:119  "첫 번째로 맞는 기동" 을 break 없이 고르는 법
for (nManeuver = 0; nManeuver < st_Target->nManeuverNum; nManeuver++)
{
    if ((st_Active == NULL) && (조건))    // ← 이미 찾았으면 st_Active != NULL 이라 통과
    {
        st_Active = st_Maneuver;
    }
}
```

## 2.4 그 밖의 규약

- **`else if` 는 반드시 `else` 로 끝난다.** 할 일이 없으면 주석만 쓴다
  (`TargetSim_JH.c:136` `case TGT_TURN_NONE: break;`, `Scenario.cpp:865` `// 열기 실패 코드 그대로`).
- **반환값을 버릴 때 `(VOID)` 로 명시한다.** `(VOID)memset(...)`, `(VOID)fprintf(...)`.
- **블록 주석 `/* */`, Doxygen `@brief` 금지.** `//` 한 줄 주석만.
- **부동소수 `==` / `!=` 금지.** 허용오차 비교를 쓴다
  (`f_Scn_IsGridMultiple`, `TGT_STEP_RATIO_TOLERANCE`).
  - 예외: `Scenario.cpp` 의 회귀 비교처럼 "비트 동일" 을 의도한 자리는 문서에만 나온다.
- **`goto`, `malloc`, `printf` 금지** (Core). UI 는 `calloc`/`free` 를 쓰되
  `new` 의 예외 대신 `NULL` 검사로 처리한다 (`Scenario.cpp:1230`).
- **인자가 바뀌지 않으면 `const`.** 거의 모든 입력 포인터가 `const ST_* *` 다.

# 3. Core — 자료구조

명세 3-(2) "본인이 정의한 표적 구조체 정의 설명 필요" 에 해당하는 절이다.

## 3.1 상수와 열거형 — `TargetSim_JH.h:12-40`

```c
#define TGT_MAX_TARGET_NUM      10      // 명세: 표적 MAX 10
#define TGT_MAX_MANEUVER_NUM    30      // 명세: 기동 MAX 30
#define TGT_MAX_STEP_NUM        100000  // 결과 버퍼 상한을 정하는 안전장치
#define TGT_MIN_STEP_TIME       1.0e-3  // [s] 나눗셈 분모의 하한

typedef enum {
    TGT_TURN_NONE  = 0,     // 명세가 지정한 값을 그대로 쓴다
    TGT_TURN_ROLL  = 1,
    TGT_TURN_YAW   = 2,
    TGT_TURN_PITCH = 3
} EN_TurnType;
```

`EN_TurnType` 의 값 0·1·2·3 은 **명세 원문의 번호와 같다.** UI 콤보 인덱스와도 같아서
(`Scenario.cpp:39` `{"0 없음", "1 Roll", "2 Yaw", "3 Pitch"}`) 변환표가 필요 없다.

## 3.2 5개 구조체의 계층

```

        ├── enTurnType    : EN_TurnType   ┐

│   ├── simTime, nStepIndex, nTargetNum
│   ├── st_Platform : ST_TargetState             104 B
│   └── st_Target[10] : ST_TargetState           104 B 씩
│       ├── simTime      : FLOAT64  [s]
│       ├── st_PosEcef   : ST_CoordRect  [m]     ← 적분은 여기서
│       ├── st_VelEcef   : ST_CoordRect  [m/s]   ← 출력·검증용
│       ├── st_Lla       : ST_CoordLla           ← 출력 + 다음 스텝 NED 기준
│       └── st_Att       : ST_CoordAtt   [rad]
└── st_Config : ST_SimConfig                  10,320 B  ← 설정의 사본
```

크기는 x64 실측값이다 (9.4절). `ST_SimState` 가 11 KB 를 넘으므로 **스택에 두면 안 되고**,
UI 는 실제로 `CSimResult` 의 멤버로 둔다 (`Scenario.h:153`). 같은 이유로
`CScenario::st_ProbeConfig` 도 멤버다 — 주석에 "10 KB 라 멤버로" 라고 적혀 있다
(`Scenario.h:123`).

## 3.3 설계 결정 네 가지

### 결정 1 — 최대 크기 배열 + 사용 개수 카운터

```c
ST_TargetInit  st_Target[TGT_MAX_TARGET_NUM];   INT32 nTargetNum;
```

동적 할당을 쓰지 않는다. 결과:

- 메모리 사용량이 시작부터 끝까지 일정하다 (실시간 시스템에서 중요한 성질).
- 표적 추가·삭제가 `nTargetNum` 숫자 하나를 바꾸는 일이 된다.
- 구조체 전체를 `=` 한 번으로 복사·비교할 수 있다 (`st_Sim->st_Config = *st_Config;`).
- 대신 `ST_SimConfig` 가 10 KB 로 커진다 — 위의 "스택 금지" 제약이 여기서 나온다.

**쓰지 않는 칸은 0 으로 채운다** (`f_Tgt_ClearState`, `TargetSim_JH.c:409`).
그러지 않으면 표·CSV·그림이 사용하지 않는 자리의 쓰레기 값을 읽는다.

### 결정 2 — 속도는 "크기(숫자) + 방향(자세각)" 으로 나눠 보관한다 ★

명세가 속도를 `V_heading` **하나**로 받으라고 했다. 그러면 방향은 자세각이 갖는다.
이 구조를 그대로 코드에 새겼다.

```c
ST_TargetInit  : headingSpeed  ← 크기. 붙박이. 절대 변하지 않는다
                 st_InitAtt    ← 방향의 출발점
ST_TargetState : st_Att        ← 방향. 매 스텝 갱신된다
                 st_VelEcef    ← 위 둘에서 매번 새로 만든 결과 (누적하지 않는다)
```

**`st_VelEcef` 는 상태가 아니라 파생값이다.** 적분기는 이 필드를 읽지 않는다.
`f_Tgt_Propagate` 는 스텝 시작 속도조차 `st_State->st_VelEcef` 에서 읽지 않고
자세·위경도에서 다시 만든다 (`TargetSim_JH.c:321`).

> 왜 중요한가 — 속도 벡터를 들고 다니며 회전시키면 그 크기가 조금씩 어긋난다.
> `V += (ω × V)·Δt` 로 어림하면 스텝마다 `√(1+(ωΔt)²)` 배로 **커진다**
> (200 m/s 가 1G 로 60초 선회하면 201.45 m/s). 크기를 숫자로 붙박아 두고
> 방향만 회전시키면 **구조적으로 속력이 변할 수 없다.**
> 9.1절 실측: 60초 동안 |V| 변동폭이 대함 7.1e-15, 대공 5.7e-14 m/s — 배정밀도 잡음 수준.

### 결정 3 — 기동 필드를 늘리지 않고 G 의 부호로 방향을 표현한다

명세가 네 가지(`TurnType`, `Gravity`, `Start`, `End`)를 못박았으므로
"오른쪽/왼쪽" 을 담을 다섯 번째 필드를 만들지 않았다.
**G 값의 부호가 회전 방향**이며, 동체축 오른손 법칙을 따른다 (`TargetSim_JH.h:41-45`).

```
Roll   (+) 우측 뱅크     (−) 좌측 뱅크
Yaw    (+) 우선회        (−) 좌선회
Pitch  (+) 기수 상승     (−) 기수 하강
```

### 결정 4 — 설정을 사본으로 들고 간다

```c
// TargetSim_JH.c:495
st_Sim->st_Config = *st_Config;     // 값 복사
```

초기화 뒤에는 엔진이 자기 사본만 본다. 사용자가 실행 도중 UI 편집칸을 고쳐도
진행 중인 시뮬레이션이 흔들리지 않는다.

주석(`TargetSim_JH.c:494`)이 짚는 미묘한 점 — 이 대입은 **설정에서 읽을 값을 전부 읽은 뒤**에
온다. 그래서 호출자가 `f_Tgt_InitSim(&sim, &sim.st_Config)` 처럼 **자기 자신을 가리켜도**
안전하다. 같은 별칭(aliasing) 안전성이 `f_Tgt_InitState`(`TargetSim_JH.c:265`),
`f_Coord_RotateVec`(`CoordinateTransform_JH.c:184`) 에도 명시적으로 들어 있다.

# 4. Core — 좌표 변환 계층

## 4.1 좌표계 규약 — `CoordinateTransform_JH.h:14-22`

헤더 맨 위 주석이 **이 프로젝트의 계약서**다. 이걸 잘못 읽으면 부호가 뒤집힌다.

```
Body    : x 전방,       y 우현,  z 하방
NED     : x 북,         y 동,    z 하
ENU     : x 동,         y 북,    z 상
Antenna : x 보어사이트, y 우측,  z 하방
az 는 보어사이트 기준 우측 회전이 (+), el 은 수평면 기준 상승이 (+)
자세각 회전 순서는 ZYX (yaw → pitch → roll)
모든 DCM 은 정규직교이므로 역변환은 전치와 같다
```

마지막 줄이 코드 전체에서 반복적으로 활용된다 (4.3절).

WGS84 상수는 **편평률에서 유도**한다. 상수를 하나만 적어 두고 나머지를 식으로 만들면
자릿수 불일치가 생기지 않는다.

```c
#define WGS84_A       6378137.0
#define WGS84_F_INV   298.257223563
#define WGS84_F       (1.0 / WGS84_F_INV)
#define WGS84_B       (WGS84_A * (1.0 - WGS84_F))
#define WGS84_E_SQ    (WGS84_F * (2.0 - WGS84_F))       // e²
#define WGS84_EP_SQ   (WGS84_E_SQ / (1.0 - WGS84_E_SQ)) // e'²
```

> 참고 소스 코드는 이심률을 8자리 리터럴(`0.08181919`)로 적었다. 그 차이가
> t=0 ECEF 위치의 0.4 mm 차이로 나타난다 (정정기록 4절).

## 4.2 DCM 생성기 네 개

| 함수 | 만드는 회전 | 줄 |
|---|---|---|
| `f_Coord_Dcm_Body_To_Ned` | `Rz(yaw)·Ry(pitch)·Rx(roll)` | `CoordinateTransform_JH.c:25` |
| `f_Coord_Dcm_Ned_To_Ecef` | 위경도로 정해지는 지역 수평 → 지구 고정 | `:67` |
| `f_Coord_Dcm_Ned_To_Enu` | 축 치환 (자기 자신이 역행렬) | `:104` |
| `f_Coord_Dcm_Ant_To_Body` | `Rz(mountYaw)·Ry(mountTilt)` | `:129` |

전부 같은 모양이다. 삼각함수를 미리 계산해 지역 배열 `dcm[9]` 에 채우고
`f_Coord_SetDcm` → `f_Mat_Load` 로 `ST_Matrix` 에 적재한다.

```c
// CoordinateTransform_JH.c:49  Rz(yaw)·Ry(pitch)·Rx(roll) 를 전개한 결과
dcm[0] = cy * cp;
dcm[1] = (cy * sp * sr) - (sy * cr);
dcm[2] = (cy * sp * cr) + (sy * sr);
dcm[3] = sy * cp;
dcm[4] = (sy * sp * sr) + (cy * cr);
dcm[5] = (sy * sp * cr) - (cy * sr);
dcm[6] = -sp;
dcm[7] = cp * sr;
dcm[8] = cp * cr;
```

행렬 곱을 실행 중에 하지 않고 **전개식을 직접 적었다.** 9번의 곱셈 대신
곱셈 12번·덧셈 6번으로 끝나고, 스텝당 여러 번 불리는 함수라 차이가 쌓인다.

`f_Coord_Dcm_Ned_To_Ecef` 의 첫 열(`-sLat·cLon, -sLat·sLon, cLat`)이 "북쪽 방향의
ECEF 성분" 이고, 둘째 열(`-sLon, cLon, 0`)이 "동쪽", 셋째 열이 "아래쪽"이다.
**열이 곧 그 지점의 단위 방향벡터**다.

## 4.3 회전 적용 — 전치가 역행렬

```c
// f_Coord_RotateVec (:161)          out = R · in
out.x = R[0][0]*x + R[0][1]*y + R[0][2]*z;      // 행으로 훑는다
/* ... */

// f_Coord_RotateVecInv (:193)       out = Rᵀ · in
out.x = R[0][0]*x + R[1][0]*y + R[2][0]*z;      // 열로 훑는다
```

**차이는 첨자 순서뿐이다.** 역행렬을 계산하지 않으므로
(a) 빠르고, (b) 수치 오차가 전혀 생기지 않고, (c) 특이행렬 걱정이 없다.
이 성질은 UI 의 궤적 그림(`CSimResult::f_ComputePoints`)과
그림에서 끌어 위치를 고치는 기능에서 그대로 쓰인다.

두 함수 모두 시작에서 `x, y, z` 를 지역 변수로 복사한다.
`f_Coord_RotateVec(&v, &dcm, &v)` 처럼 **입출력이 같은 객체여도 되게 하기 위함**이다.

## 4.4 LLA ↔ ECEF

**정방향** (`:233`) — 교과서 식 그대로.

```c
primeVertical = WGS84_A / sqrt(1.0 - (WGS84_E_SQ * sLat * sLat));      // N(φ)
out->x = (N + alt) * cLat * cLon;
out->y = (N + alt) * cLat * sLon;
out->z = ((N * (1.0 - WGS84_E_SQ)) + alt) * sLat;
```

**역방향** (`:268`) — **Bowring 폐형식 해**. 이 프로젝트가 참고 소스에서 바꾼 유일한 식이다.

```c
p      = sqrt(x² + y²);
theta  = atan2(z * WGS84_A, p * WGS84_B);                          // 보조 위도
lat    = atan2(z + e'²·b·sin³θ,  p − e²·a·cos³θ);                   // 반복 없이 한 번에
alt    = (p·cosφ) + (z·sinφ) − N·(1 − e²·sin²φ);                    // 1/cosφ 를 피한 형태
```

세 가지가 중요하다.

1. **반복이 없다.** 참고 소스는 같은 계산을 5회 반복해 근사했다. 그 5회가 충분한지
   보장이 없고 고위도에서 고도가 크게 어긋났다 (위도 89.9°·고도 300 m 에서 3.6 m).
   Bowring 은 지구 근방에서 mm 수준이다.
2. **고도식이 `1/cos φ` 를 쓰지 않는다.** 극 근처에서 발산하지 않는다.
   헤더 주석 `:267` 이 이 점을 명시한다.
3. **극점 특이점을 따로 처리한다** (`:287`). `p < 1e-9` 이면 경도를 0 으로 두고
   위도를 ±90°, 고도를 `|z| − b` 로 준다. `atan2(0, 0)` 을 피한다.

> **왜 이 함수가 정확도의 병목인가** — 5.6절의 적분은 매 스텝 ECEF→LLA 를 **두 번** 부른다
> (중점 위치, 최종 위치). 그 LLA 가 다음 회전 행렬의 기준이 되므로,
> 이 변환이 부정확하면 궤적 전체가 부정확해진다.

## 4.5 조합 변환과 벡터 유틸

| 함수 | 구현 | 쓰이는 곳 |
|---|---|---|
| `f_Trans_Body_To_Ned` (`:451`) | DCM 생성 → `RotateVec` | **속도 생성 1단계** |
| `f_Trans_NedVec_To_Ecef` (`:539`) | DCM 생성 → `RotateVec` | **속도 생성 2단계** |
| `f_Trans_EcefVec_To_Ned` (`:555`) | DCM 생성 → `RotateVecInv` | 그림 좌표 |
| `f_Trans_Ned_To_Ecef` (`:571`) | 회전 + 기준점 **더하기** | 그림에서 끌어 위치 고치기 |
| `f_Trans_Ecef_To_Ned` (`:594`) | 기준점 **빼기** + 역회전 | 그림 좌표 |

> **`f_Trans_NedVec_To_Ecef` 와 `f_Trans_Ned_To_Ecef` 를 혼동하지 말 것.**
> 앞은 **벡터**(속도·방향) 변환으로 회전만 한다. 뒤는 **점**(위치) 변환으로
> 회전 뒤 기준점을 더한다. 속도에 기준점을 더하면 당연히 틀린다.
> 참고 소스는 이 둘이 한 함수였고(`Pf = 0` 인자로 구분), `_JH` 판은 회전 부분을
> 따로 떼어 이름으로 구분했다.

`f_Coord_WrapAngle` (`:706`) 은 각도를 `(−π, π]` 로 접는다.

```c
wrapped = fmod(angle + PI, TWO_PI);
if (wrapped < 0.0) { wrapped += TWO_PI; }      // fmod 는 피제수의 부호를 따른다
return wrapped - PI;
```

`fmod` 가 음수를 돌려줄 수 있으므로 보정이 필요하다. 이것이 자세각이 무한정
커지지 않게 막는다 — 60초 × 2G 선회면 yaw 가 1000° 를 넘는다.

```c
           (st_Config->st_Platform.headingSpeed < HUGE_VAL)))
```

`speed < 0.0` 로 쓰면 NaN 은 `false` 라 통과한다.
**"올바른 범위 안에 있는가" 를 묻고 그것을 부정하면** NaN 이 걸린다.
`f_Tgt_GetStepNum` (`:191`) 도 같은 방식이다 — 주석이 명시한다.

### 플랫폼은 0 m/s 허용, 표적은 불허

```c
// :217  플랫폼
headingSpeed >= 0.0                 // 0 허용
// :38   표적 (f_Tgt_CheckTarget)
if (st_Target->headingSpeed <= 0.0) { enStatus = TGT_ERR_SPEED; }   // 0 불허
```

이유는 **나눗셈**이다. 기동 각속도가 `ω = n·g / V` 라서 표적 속력이 0 이면 터진다.
플랫폼은 기동이 없어 이 나눗셈을 아예 지나가지 않는다.
명세 시나리오의 플랫폼 속도가 0 m/s 이므로 이 구분이 필요했다.
`f_Tgt_StepPlatformAt` (`:393`) 의 주석이 이 사실을 못박는다.

### 스텝 수 산출 — `f_Tgt_GetStepNum` (`:184`)

```c
if ((stepTime >= TGT_MIN_STEP_TIME) && (durationTime >= stepTime))   // 긍정형 → NaN 탈락
{
    ratio   = durationTime / stepTime;         // 60.0/0.1 = 600.0 (정확)
    nearest = floor(ratio + 0.5);              // 반올림

    if ((nearest <= (FLOAT64)TGT_MAX_STEP_NUM) &&
        (fabs(ratio - nearest) <= TGT_STEP_RATIO_TOLERANCE))    // 1e-6
    {
        nStepNum = (INT32)nearest;             // ← 범위 확인 뒤에만 정수 변환
    }
}
```

세 가지 방어가 겹쳐 있다.

1. **정수배 강제.** 마지막 스텝만 길이가 다른 상황을 만들지 않는다.
2. **허용오차 1e-6.** `0.3 / 0.1 = 2.9999999999999996` 처럼 정수배인데도 몫이
   정수로 안 나오는 경우가 있다. (60.0/0.1 은 배정밀도에서 정확히 600.0 이다.)
3. **정수 변환 전 범위 확인.** 범위 밖 또는 NaN 인 실수를 `INT32` 로 변환하는 것은
   C 표준상 **미정의 동작**이다. `nearest <= TGT_MAX_STEP_NUM` 을 먼저 본다.

### 기동 구간 규칙 — `[start, end)` 반열린 구간

```c
// :75-88
// 구간을 [startTime, endTime) 로 보므로 한 기동의 끝과 다른 기동의 시작이 같은 것은 겹침이 아니다.
if ((st_Maneuver->startTime < st_Other->endTime) &&
    (st_Other->startTime < st_Maneuver->endTime))    -> TGT_ERR_MANEUVER_OVERLAP
```

명세가 정하지 않은 세 가지를 여기서 정한다.

- **끝 시각은 포함하지 않는다.** `[0,20)` 과 `[20,40)` 을 빈틈도 겹침도 없이 이을 수 있다.
  정하지 않으면 20.0초 정각이 앞 기동에 먹혀 뒤 기동이 한 스텝을 잃는다.
  200 m/s 1G 기준으로 그 한 스텝은 0.281°, 남은 30초 동안 약 **29 m** 어긋난다.
- **진짜로 겹치면 실행 전에 거부한다.** 합성 규칙은 명세에 없다.
  "모르는 입력을 추측해서 처리하는 것보다 거부하는 편이 정직하다."
- **겹침 판정은 O(n²)** 이지만 n ≤ 30 이라 문제되지 않는다.

> 9.3절에서 `[0,20)+[20,40)` 은 `TGT_OK`, `[0,20)+[10,30)` 은 `TGT_ERR_MANEUVER_OVERLAP`
> 임을 직접 확인했다.

## 5.3 초기화 — `f_Tgt_InitState` (`:253`) / `f_Tgt_InitSim` (`:448`)

`f_Tgt_InitState` 는 **지역 변수 `st_New` 에 전부 채운 뒤 마지막에 한 번 옮긴다.**

```c
ST_TargetState st_New;                       // 지역 사본

st_New.simTime      = 0.0;
st_New.st_Lla       = *st_InitLla;
st_New.st_Att.roll  = f_Coord_WrapAngle(st_InitAtt->roll);       // Yaw 270° → −90°
/* ... */
enCoord = f_Trans_Lla_To_Ecef(&st_New.st_PosEcef, &st_New.st_Lla);
if (enCoord == COORD_OK) { enCoord = f_Tgt_GetVelEcef(&st_New.st_VelEcef, ...); }

if (enCoord == COORD_OK) { *st_State = st_New;  enStatus = TGT_OK; }   // ← 전부 성공해야
else                     { enStatus = TGT_ERR_COORD; }                 //    반영한다
```

두 가지를 한꺼번에 얻는다.

- **원자성** — 중간에 실패하면 `*st_State` 는 손대지 않은 원래 값 그대로다.
- **별칭 안전** — 입력이 `st_State` 의 멤버를 가리켜도 된다 (주석 `:265`).

`f_Tgt_InitSim` 의 루프가 특이하다.

```c
// :462  nTargetNum 이 아니라 TGT_MAX_TARGET_NUM 까지 돈다
for (nTarget = 0; nTarget < TGT_MAX_TARGET_NUM; nTarget++)
{
    if (nTarget < nTargetNum) { ... f_Tgt_InitState(...) ... }
    else                      { f_Tgt_ClearState(&st_New.st_Target[nTarget]); }
}
```

**쓰지 않는 칸까지 10개를 전부 순회해 0 으로 채운다.** 결과 표·CSV·그림이
초기화되지 않은 메모리를 읽을 가능성을 원천 차단한다.

## 5.4 ★ 동체 속도 → ECEF 속도 — `f_Tgt_GetVelEcef` (`:163`)

**명세가 "고민해보시오" 라고 한 항목이고, 이 과제의 핵심이다.**

```c
static EN_CoordStatus f_Tgt_GetVelEcef(ST_CoordRect *st_VelEcef, const ST_CoordAtt *st_Att,
                                       const ST_CoordLla *st_Lla, FLOAT64 headingSpeed)
{
    st_VelBody.x = headingSpeed;     // 기수 방향
    st_VelBody.y = 0.0;              // 옆으로 미끄러지지 않는다
    st_VelBody.z = 0.0;              // 위아래로 미끄러지지 않는다

    enStatus = f_Trans_Body_To_Ned(&st_VelNed, &st_VelBody, st_Att);

    if (enStatus == COORD_OK)
    {
        enStatus = f_Trans_NedVec_To_Ecef(st_VelEcef, &st_VelNed, st_Lla->lat, st_Lla->lon);
    }
    return enStatus;
}
```

### 왜 회전이 두 번인가

```
V_body = (V, 0, 0)                        기수 방향으로 V
   │  ① C_body→ned(roll, pitch, yaw)       "내가 선 자리에서 북·동·아래 성분"
   ▼
V_ned  = (V_N, V_E, V_D)
   │  ② C_ned→ecef(lat, lon)               "지구 좌표 성분"
   ▼
V_ecef = (V_x, V_y, V_z)
```

**Yaw 180° 는 "남쪽을 보고 있다" 는 뜻인데, "남쪽" 이 지구 좌표로 어느 방향인지는
내가 어디에 서 있느냐에 따라 다르다.** 서울의 남쪽과 브라질의 남쪽은 우주에서 보면
완전히 다른 방향이다. 자세각은 **상대적** 정보이고, 절대 방향이 되려면 위치가 필요하다.
그래서 `f_Tgt_GetVelEcef` 가 `st_Lla` 를 인자로 받는다.

### 놓치기 쉬운 세 가지

1. **두 번째 회전은 현재 위치에 따라 달라진다.** 표적이 움직였으면 행렬을 다시 만들어야 한다.
   처음 위치의 행렬을 재사용하면 이동한 거리만큼 지구가 휜 것을 무시하게 되고, 오차가 쌓인다.
2. **회전 행렬은 크기를 바꾸지 않는다.** 200 m/s 를 두 번 돌려도 200 m/s 다.
   결정 2(3.3절)의 "속력이 구조적으로 보존된다" 가 여기서 완성된다.
3. **되돌릴 때는 전치만 하면 된다.** 4.3절의 성질. 그림 그리기에서 쓴다.

### t=0 확인값 (9.1절에서 직접 재현)

| 표적 | 자세 | ECEF 속도 [m/s] | 크기 |
|---|---|---|---|
| 대함 32.125°N 126.03°E, 30 m/s | Yaw 270° (서) | `(24.2613, 17.6463, 0.0000)` | 30.000000000 |
| 대공 32.12°N 126.0°E, 200 m/s | Yaw 180° (남) | `(−62.5044, 86.0299, −169.3873)` | 200.000000000 |

> 대공 표적의 `V_z` 가 음수인 것은 **고도가 내려가서가 아니다.** ECEF 의 z 는 북극 방향이고,
> 남쪽으로 가면 그 성분이 줄기 때문이다. 실제 고도는 60초 뒤에도 정확히 300 m 다.

## 5.5 기동 해석 — `f_Tgt_GetAttRate` (`:99`)

"지금 시각에 어떤 기동이 걸려 있는가" 를 판정해 **각속도 3성분**을 돌려준다.

```c
st_Rate->roll = st_Rate->pitch = st_Rate->yaw = 0.0;      // 기본은 회전 없음

enStatus = f_Tgt_CheckTarget(st_Target);        // ← 검증 없이 불릴 수도 있으므로 여기서도 확인

if (enStatus == TGT_OK)
{
    evalTime = simTime + TGT_TIME_EPSILON;      // 1e-6

    for (nManeuver = 0; nManeuver < st_Target->nManeuverNum; nManeuver++)
    {
        if ((st_Active == NULL) &&                              // 첫 번째 것만
            (st_Maneuver->startTime <= evalTime) &&
            (evalTime < st_Maneuver->endTime))                  // [start, end)
        {
            st_Active = st_Maneuver;
        }
    }

    if (st_Active != NULL)
    {
        omega = (st_Active->gravityValue * G_FORCE) / st_Target->headingSpeed;

        switch (st_Active->enTurnType)
        {
        case TGT_TURN_NONE:                           break;
        case TGT_TURN_ROLL:   st_Rate->roll  = omega; break;
        case TGT_TURN_YAW:    st_Rate->yaw   = omega; break;
        case TGT_TURN_PITCH:  st_Rate->pitch = omega; break;
        default:              enStatus = TGT_ERR_TURN_TYPE; break;
        }
    }
}
```

### `TGT_TIME_EPSILON` 이 필요한 이유

`curTime` 은 `nStepIndex × stepTime` 으로 만든다. 0.1 은 이진 부동소수로 정확히
표현되지 않으므로 `200 × 0.1` 이 `20.000000000000004` 처럼 10진 기동 시각보다
아주 조금 클 수도, 작을 수도 있다. `simTime + 1e-6` 으로 비교해 이 잡음을 흡수한다
(주석 `:5`).

### `ω = n·g / V` 의 유도

원운동에서 구심가속도는 `a = V·ω`. 명세의 Gravity Value 는 이 가속도를 중력의 몇 배로
줬는지를 뜻하므로 `V·ω = n·g` → `ω = n·g / V`.

여기서 두 가지가 바로 따라 나온다.

```
선회 반경  R = V / ω = V² / (n·g)
선회 주기  T = 2π/ω = 2π·V / (n·g)
```

| 속력 | G | 각속도 | 선회 반경 | 한 바퀴 | Δt=0.1s 회전각 |
|---|---|---|---|---|---|
| 30 m/s | 1G | 18.7 °/s | 92 m | 19.2 s | 1.87° |
| 30 m/s | 2G | 37.5 °/s | 46 m | 9.6 s | 3.75° |
| 200 m/s | 1G | 2.8 °/s | 4,079 m | 128.1 s | 0.28° |
| 200 m/s | 2G | 5.6 °/s | 2,039 m | 64.1 s | 0.56° |

**같은 G 라도 느린 표적이 훨씬 급하게 돈다.** 익숙한 감각과 반대라 처음에는 헷갈린다.
이 두 식은 UI 의 기동 표에도 그대로 나온다 (`TargetSimUIDlg.cpp:904`).

### Roll 은 왜 궤적을 바꾸지 않는가

`TurnType` 을 글자 그대로 **"어느 축을 돌리는가"** 로 해석했다.
속도는 `C_ned→ecef · C_body→ned(roll,pitch,yaw) · (V,0,0)` 인데,
`(V,0,0)` 은 **동체 x 축 위의 벡터**이고 roll 은 **x 축 둘레의 회전**이다.
자기 회전축 위의 벡터는 회전해도 그대로다. 따라서 roll 각이 아무리 변해도
`C_body→ned · (V,0,0)` 은 변하지 않는다.

> 9.3절 실측: Roll 1G 를 60초 건 궤적이 직진 궤적과 **ECEF 비트 단위로 동일**하고,
> roll 각만 168.5639° 로 변했다. 코드로 `if (roll) skip` 같은 특별 처리를 하지 않았는데도
> 그렇게 된다 — 수학이 알아서 해 준다.

`gravityValue` 가 Roll 에서는 물리적 의미가 없지만(구심가속도와 무관),
"Gravity Value 하나로 세 축을 다룬다" 는 명세를 지키려고 같은 식을 쓴다 (주석 `:131`).

## 5.6 ★★ 한 스텝 전진 — `f_Tgt_Propagate` (`:294`)

**엔진에서 가장 중요한 함수다.** 여기가 정확도를 결정한다.

### 문제 설정

0.1초마다 위치를 갱신한다는 것은 **그 0.1초 동안 속도가 변하지 않는다고 치고 직선으로
옮긴다**는 뜻이다. 그러면 "변하지 않는다고 칠 그 속도" 를 구간 어느 시점에서 뽑을지
정해야 한다.

- **시작 시점(0초)의 방향** — Euler 법. 가장 단순. 채택하지 않음.
- **한가운데(0.05초)의 방향** — **중점법(RK2)**. 이쪽으로 구현.

곡선 아래 넓이를 직사각형으로 어림할 때 왼쪽 끝 높이로 재느냐 가운데 높이로 재느냐의
차이와 같다. 가운데로 재면 모자란 쪽과 남는 쪽이 상쇄된다.

### 실제 코드의 10단계

속도가 `C(위경도) · C(자세) · (V,0,0)` 이므로, **한가운데의 방향을 얻으려면
한가운데의 자세와 한가운데의 위치가 둘 다 필요하다.**

```c
halfStep = 0.5 * stepTime;

// ① 중점 자세 (wrap 하지 않는다 — 곧 회전에 쓰일 뿐이다)
st_AttMid.roll  = st_State->st_Att.roll  + (st_Rate->roll  * halfStep);
st_AttMid.pitch = st_State->st_Att.pitch + (st_Rate->pitch * halfStep);
st_AttMid.yaw   = st_State->st_Att.yaw   + (st_Rate->yaw   * halfStep);

// ② 종단 자세 (상태로 남으므로 wrap 한다)
st_Next.st_Att.roll  = f_Coord_WrapAngle(st_State->st_Att.roll  + (st_Rate->roll  * stepTime));
st_Next.st_Att.pitch = f_Coord_WrapAngle(...);
st_Next.st_Att.yaw   = f_Coord_WrapAngle(...);

// ③ 스텝 시작 속도 — 상태의 st_VelEcef 를 읽지 않고 다시 만든다
enCoord = f_Tgt_GetVelEcef(&st_VelStart, &st_State->st_Att, &st_State->st_Lla, headingSpeed);

// ④ 중점 위치 예측 (방향을 정하는 데만 쓰고 버린다)
f_Coord_VecScale(&st_Delta, &st_VelStart, halfStep);
f_Coord_VecAdd(&st_PosMid, &st_State->st_PosEcef, &st_Delta);

// ⑤ 중점 위경도
f_Trans_Ecef_To_Lla(&st_LlaMid, &st_PosMid);

// ⑥ ★ 중점 속도 — 중점 자세 + 중점 위경도
f_Tgt_GetVelEcef(&st_VelMid, &st_AttMid, &st_LlaMid, headingSpeed);

// ⑦ 이동 — 출발점은 P_k 그대로, 속도만 중점값
f_Coord_VecScale(&st_Delta, &st_VelMid, stepTime);
f_Coord_VecAdd(&st_Next.st_PosEcef, &st_State->st_PosEcef, &st_Delta);

// ⑧ 새 위경고도
f_Trans_Ecef_To_Lla(&st_Next.st_Lla, &st_Next.st_PosEcef);

// ⑨ 보고용 속도 (다음 스텝은 이 값을 쓰지 않는다 — ③ 에서 다시 만든다)
f_Tgt_GetVelEcef(&st_Next.st_VelEcef, &st_Next.st_Att, &st_Next.st_Lla, headingSpeed);

// ⑩ 전부 성공했을 때만 반영
if (enCoord == COORD_OK) { st_Next.simTime = nextTime;  *st_State = st_Next; }
```

**스텝당 비용** — `f_Tgt_GetVelEcef` 3회(= DCM 6개 생성), `f_Trans_Ecef_To_Lla` 2회.

### 얼마나 차이가 나는가 — 9.2절 실측

200 m/s 표적이 1G 로 선회하는 조건에서 60초를 돌린 뒤 위치 오차
(기준: 같은 계산을 Δt=0.001 로 잘게 돌린 결과).

| Δt | Euler (시작 방향) | 중점법 | 중점법 비 |
|---|---|---|---|
| 0.1 s | 19.91 m | **0.008122 m** | — |
| 0.05 s | 9.95 m (**½**) | **0.002030 m** | **0.250** |
| 0.025 s | 4.98 m (**½**) | **0.000507 m** | **0.250** |

**Δt 를 절반으로 줄이면 Euler 는 오차가 절반, 중점법은 4분의 1이 된다.**
이것이 2차 정확도의 직접 증거다. 같은 정확도를 Euler 로 내려면 Δt 를 약 2,500배
잘게 쪼개야 하고, 계산량도 2,500배가 된다.
**계산은 조금 느는데(스텝당 속도 생성 2회·좌표변환 1회) 정확도는 2,500배 올라가므로**
더 복잡한 RK4 까지 갈 이유가 없었다.

### Euler 오차의 정체

시작 방향을 쓰면 매 스텝 방향이 반 스텝치만큼 뒤처지므로, 궤적이 통째로
**반 스텝 이동거리**만큼 옆으로 밀린다.

```
밀림 = V·Δt / 2 = 200 × 0.1 / 2 = 10 m       (원의 중심이 10 m 옮겨간다)
```

이 밀림은 시간이 갈수록 커지지 않고 일정하다. 다만 원 위 어디에 있느냐에 따라
실제 위치와의 거리가 달라져 반 바퀴쯤에서 최대 `V·Δt = 20 m` 가 된다.
60초는 168.6° 선회이므로 거의 최대치인 19.9 m 가 나온다.

### ⚠ ④⑤ 를 빠뜨리면 생기는 일 — 이 코드가 한 번 틀렸던 자리

최초 구현은 중점 **자세**만 쓰고, NED→ECEF 회전은 스텝 **시작** 위경도로 만들었다.
0.1초에 20 m 가는 동안 지역 수평 방향이 돌아가는 양이 0.0002° 뿐이라 무시해도 된다고 봤다.

| | 시작 위치로 회전 (최초) | 중점 위치로 회전 (현재) |
|---|---|---|
| 대공 표적 60초 뒤 고도 (수평 비행) | 300.0189 m | **300.000000 m** |
| 1G 선회 60초 위치 오차 | 0.0215 m | **0.0081 m** |
| Δt 절반 → 오차 비 | 0.41~0.48 (**1차**) | **0.250** (2차) |

**수평 비행인데 고도가 올랐다.** 둥근 지구 위에서 출발점의 수평 방향으로 직선 20 m 를
가면 도착 지점에서는 고도가 `d²/(2R) = 0.03 mm` 높다. 한 번은 작아도 600번 모두 같은 쪽으로
쌓여 1.9 cm 가 된다. 중점 위치의 수평 방향은 출발점의 수평보다 아주 조금 아래를 향하므로,
그 방향으로 가면 앞 절반에 내려간 만큼 뒤 절반에 올라와 고도가 제자리로 돌아온다.

> **교훈** — 중점법은 **상태 전체**(자세 **와** 위치)를 한가운데 값으로 써야 성립한다.
> 하나라도 시작 값을 쓰면 그 부분이 1차로 떨어지고, 전체가 1차가 된다.
> 그리고 그 사실은 "Δt 를 절반으로 줄여 오차 비를 본다" 는 검사로만 드러난다.
> 절대 오차만 보면 0.021 m 도 충분히 작아 보인다.

## 5.7 스텝 진행 — `f_Tgt_StepSim` (`:506`)

```c
st_Config = &st_Sim->st_Config;

// ① 매 호출 재검증 — ST_SimState 는 공개 구조체라 호출 사이에 외부에서 망가질 수 있다
if (f_Tgt_ValidateConfig(st_Config) != TGT_OK)                       -> TGT_ERR_SIM_STATE
else if ((f_Tgt_GetStepNum(st_Config) != st_Sim->nStepNum) ||        // 정합성
         (nStepIndex < 0) || (nStepIndex > nStepNum) ||
         (st_Sim->st_Sample.nTargetNum != st_Config->nTargetNum))    -> TGT_ERR_SIM_STATE
else if (nStepIndex == nStepNum)                                     -> TGT_ERR_SIM_END
else {
    // ② 시각은 누적이 아니라 곱셈
    curTime  = (FLOAT64)nStepIndex * stepTime;
    nextTime = (FLOAT64)nNextIndex * stepTime;

    // ③ 표본 사본에서 전부 진행
    st_Next = st_Sim->st_Sample;

    enStatus = f_Tgt_StepPlatformAt(&st_Next.st_Platform, &st_Config->st_Platform, stepTime, nextTime);

    for (nTarget = 0; nTarget < nTargetNum; nTarget++) {
        if (enStatus == TGT_OK) {
            enStatus = f_Tgt_StepTargetAt(&st_Next.st_Target[nTarget],
                                          &st_Config->st_Target[nTarget], stepTime, curTime, nextTime);
        }
    }

    // ④ 전원 성공했을 때만 커밋
    if (enStatus == TGT_OK) { st_Next.nStepIndex = nNextIndex;  st_Next.simTime = nextTime;
                              st_Sim->st_Sample = st_Next; }
}
```

### ① 매 호출 재검증하는 이유

`ST_SimState` 는 헤더에 공개된 구조체라 호출자가 언제든 고칠 수 있다.
배열 인덱스(`st_Config->st_Target[nTarget]`)와 나눗셈의 근거를 매번 다시 세운다.
주석 `:527` 가 이 의도를 적는다. 비용은 스텝당 O(표적수 × 기동수²) 이지만
최악(10 × 30²)에서도 무시할 수준이다.

### ② 시각을 곱셈으로 만드는 이유 ★

0.1 은 이진 부동소수로 정확히 표현되지 않는다 (`0.1000000000000000055511151231257827…`).

```
누적:  t += 0.1  을 600번  →  60.00000000000058     (오차 5.8e-13)
곱셈:  t = 600 * 0.1       →  60.0                  (정확)
```

**기동 구간 판정이 이 시각을 쓰므로, 누적 오차가 곧 기동 시점 오차가 된다.**
`TGT_TIME_EPSILON` 이 흡수할 수 있는 크기이긴 하지만, 애초에 만들지 않는 편이 낫다.

> 9.1절 실측: 600 스텝 뒤 `simTime` 이 정확히 `60.000000` 이다.
> 참고로 `f_Tgt_StepTarget` 단독 루프(하네스용 API)는 `st_State->simTime + stepTime` 으로
> 누적하므로 60.000000000000583 이 나온다 — 두 경로의 의도된 차이다.

### ③④ 사본 후 일괄 커밋

표적 1은 진행하고 표적 2에서 실패하면 **한 표본 안에 서로 다른 시각의 상태가 섞인다.**
사본에서 전부 끝낸 뒤 한 번에 옮기면 그런 중간 상태가 외부에 노출되지 않는다.
`f_Tgt_InitState`(5.3절), `f_Tgt_Propagate`(5.6절 ⑩)와 같은 패턴 —
**이 코드베이스는 "전부 성공 아니면 아무 것도 안 함" 을 세 계층에서 반복한다.**

## 6.4 오류 위치 탐침 — `f_LocateCoreError` (`Scenario.cpp:709`)

Core 는 `TGT_ERR_MANEUVER_OVERLAP` 이라고만 알려 주지 **어느 기동인지는 말해 주지 않는다.**
Core 를 고쳐 위치를 반환하게 만들 수도 있지만, 그러면 Core API 가 UI 사정에 오염된다.

**대신 이분 탐색 대신 증분 재검증을 쓴다.**

```c
st_ProbeConfig = *st_Config;

// 1단계: 기동을 전부 빼고 검증 → 시간·속력·표적 수 오류인지 본다

enProbe = f_Tgt_ValidateConfig(&st_ProbeConfig);
if (enProbe == TGT_ERR_TIME)  { /* 시뮬레이션 시간 칸 */ }
else if (enProbe == TGT_ERR_SPEED) { /* 플랫폼 속력 칸 */ }

// 2단계: 표적을 하나씩, 기동을 하나씩 늘려 가며 처음 실패하는 지점을 찾는다
for (nTarget = 0; ...; nTarget++) {
    st_ProbeConfig.nTargetNum   = 1;
    st_ProbeConfig.st_Target[0] = st_Config->st_Target[nTarget];
    for (nManeuver = 0; ...; nManeuver++) {
        st_ProbeConfig.st_Target[0].nManeuverNum = nManeuver + 1;   // 0→1→2→…
        if (f_Tgt_ValidateConfig(&st_ProbeConfig) != TGT_OK) { /* 여기가 범인 */ }
    }
}
```

**핵심은 "Core 의 판정을 그대로 두고, 위치만 찾는다" 는 것.**
같은 판정 논리를 UI 에 복제하지 않았으므로 두 벌이 어긋날 일이 없다.

찾은 뒤에는 `TGT_ERR_TIME` 을 다시 나눠 시작 칸인지 종료 칸인지까지 가른다 (`:767`).

```c
if ((enProbe == TGT_ERR_TIME) && (st_Bad->startTime >= 0.0) &&
    ((st_Bad->endTime <= st_Bad->startTime) || (st_Bad->endTime > st_Config->durationTime)))
{
    nField = SCN_FIELD_END;      // 종료가 문제
}
```

결과는 `ST_ScnIssue` (`Scenario.h:72`) 에 담겨 `f_MarkIssue` 가 해당 칸을 붉게 칠한다.
**메시지 상자를 띄우지 않고 포커스도 옮기지 않는다** — 치던 값을 잃지 않게.

## 6.5 `CSimResult` — 실행과 2단 버퍼 (`Scenario.h:127`)

```c
class CSimResult {
    ST_SimState    st_Sim;               // 엔진 상태 (11 KB)

    ST_SimSample  *st_SampleBuf;         // ← 현재 화면이 보는 결과
    ST_PlotPoint  *st_PointBuf;
    INT32          nSampleNum, nObjectNum;

    ST_SimSample  *st_PendingSample;     // ← 방금 계산한 새 결과
    ST_PlotPoint  *st_PendingPoint;
    INT32          nPendingSampleNum, nPendingObjectNum;
};
```

**왜 두 벌인가** — 사용자가 값을 고칠 때마다 자동 실행되는데, 그 실행이 실패하면
화면이 비면 안 된다. 새 결과가 **완전히 성공했을 때만** 교체한다.

```c
f_Run()       새 버퍼 calloc → 601 표본 채움 → 그림 좌표까지 성공 → st_Pending* 에 둔다
              (한 번이라도 실패하면 free 하고 0 을 돌려준다. st_SampleBuf 는 그대로)
f_Commit()    free(현재) → 현재 = pending → pending = nullptr
```

호출 순서가 중요하다 (`TargetSimUIDlg.cpp:1619`).

```c
f_StopPlay();                                              // ① 재생 중지
st_Plot.f_SetResult(nullptr);                              // ② 그림이 옛 버퍼를 놓게
st_ResultList.SetItemCountEx(0, LVSICF_NOINVALIDATEALL);   // ③ 표가 옛 버퍼를 놓게
st_Result.f_Commit();                                      // ④ 그제야 free + 교체
```

②③ 을 빼먹으면 `f_Commit` 의 `free` 뒤에 그림이나 표가 해제된 메모리를 읽는다.
**주석 `TargetSimUIDlg.cpp:1618` 이 "표와 그림이 옛 버퍼를 가리키지 않게 먼저 끊고 바꾼다" 로 이 순서를 못박는다.**

### 메모리 계산 (`Scenario.cpp:1227`)

```c
sampleBytes = nNewSampleNum * sizeof(ST_SimSample);          // 601 × 1160 = 697 KB
pointBytes  = nNewSampleNum * nNewObjectNum * sizeof(ST_PlotPoint);

st_NewSample = (ST_SimSample *)calloc(nNewSampleNum, sizeof(ST_SimSample));
st_NewPoint  = (ST_PlotPoint *)calloc(nNewSampleNum * nNewObjectNum, sizeof(ST_PlotPoint));

if ((st_NewSample == nullptr) || (st_NewPoint == nullptr)) {
    st_Error->Format(_T("메모리 부족: 결과 버퍼에 약 %.0f MB 가 필요합니다"), ...);
}
```

곱셈을 전부 `UINT64` 로 한다 — `INT32` 로 하면 최악(100,001 × 1,160 = 116 MB)에서
오버플로한다. `new` 대신 `calloc` 을 쓰는 이유는 주석대로 **"예외 대신 NULL 로 받으려고"**.
최악 조건에서 실패는 현실적인 시나리오이고, 예외를 던지는 것보다 문구를 보여 주는 편이 낫다.

### 그림 좌표 — `f_ComputePoints` (`Scenario.cpp:1290`)

ECEF 를 그대로 그리면 축 값이 3.2e6 수준이고 원점이 지구 중심이라 궤적이 보이지 않는다.
**표본 0 의 플랫폼 위치를 원점으로 하는 국소 NED 평면**으로 옮긴다.

```c
// 기준 DCM 은 한 번만 만든다  ← f_Trans_Ecef_To_Ned 를 점마다 부르면 601×3 = 1,803회 생성
f_Coord_Dcm_Ned_To_Ecef(&st_Dcm, st_Origin->st_Lla.lat, st_Origin->st_Lla.lon);

for (nStep …) for (nObject …) {
    if (f_Res_IsStateFinite(st_State) == 0) { /* NaN/Inf 마지막 방어선 */ }
    f_Coord_VecSub(&st_Diff, &st_State->st_PosEcef, &st_Origin->st_PosEcef);
    f_Coord_RotateVecInv(&st_Ned, &st_Dcm, &st_Diff);      // 전치 = 역변환
    st_Point[…].east  = st_Ned.y;
    st_Point[…].north = st_Ned.x;
}
```

`f_Res_IsStateFinite` (`:1121`) 가 10개 필드를 전부 `isfinite` 로 확인한다.
**그림·표·CSV 에 비유한 값이 나가지 않게 하는 마지막 방어선**이다.

### 출력 서식 — `f_FormatCell` (`Scenario.cpp:1415`)

표와 CSV 가 **같은 함수**를 쓴다. 두 벌이 어긋날 일이 없다.

```
열 0        스텝 번호        %d
열 1        시각             %.3f            (1 ms 격자이므로 3자리로 정확)
열 2+3k     위도 [°]         %.9f            (1e-9° ≈ 0.1 mm)
열 3+3k     경도 [°]         %.9f
열 4+3k     고도 [m]         %.4f
```

`f_Num_FormatFixed` (`UiCommon.cpp:54`) 가 **`-0.0000` 의 부호를 뗀다.**
플랫폼 고도가 역변환 반올림으로 −9.3e-10 m 가 되는데, `%.4f` 로 쓰면 `-0.0000` 이 된다.
**정지한 플랫폼의 고도가 음수로 보이는 것은 오해를 부른다.**

## 6.6 화면 부품

### `CGridCtrl` (`GridCtrl.h:67`) — 칸을 바로 고치는 표

`CListCtrl` 을 전부 커스텀 드로우하고, 칸 위에 편집칸(`CGridEdit`)·스핀·콤보를 띄운다.

| 열 종류 | 동작 |
|---|---|
| `GRID_KIND_LABEL` | 읽기 전용 + 행 색 표식 |
| `GRID_KIND_NUMBER` | 편집칸 + ▲▼ 스핀 |
| `GRID_KIND_CHOICE` | 콤보 목록 |
| `GRID_KIND_VALUE` | 읽기 전용 계산값 (회전각·선회 반경) |
| `GRID_KIND_CUSTOM` | 부모가 그린다 (기동 구간 띠) |

- 편집 열기: 선택된 칸 재클릭 / 더블클릭 / F2 / Enter / Space / **숫자를 그냥 침**
- 증감: ▲▼, ↑↓, 휠. Ctrl 로 10배. 증감 폭은 열마다 다르다
  (위경도 0.001°, 고도 10 m, 속력 1 m/s, 각 1°, G 0.1, **기동 시각 = Δt**)
- 증감은 **편집을 닫지 않고 바로 반영**되어 값을 굴리는 동안 그림이 따라 움직인다
- Esc 되돌림, Tab/Shift+Tab 다음·이전 편집 칸

기동 시각의 증감 폭이 Δt 인 것이 영리하다 — 증감만 쓰면 **격자를 벗어날 수 없다**
(`f_UpdateTimeNudge`, `TargetSimUIDlg.cpp:954`).

`CGridEdit::OnGetDlgCode` 가 `DLGC_WANTALLKEYS` 를 돌려주는 이유는
**Enter/Tab/Esc 를 대화상자에 빼앗기지 않기 위해서**다 (`GridCtrl.h:45` 주석).

### `CTrajectoryPlot` (`TrajectoryPlot.h:28`) — 궤적 그림

두 패널: **동–북 평면(등축척)** + **고도–시각**.
가로가 세로의 1.4배를 넘으면 나란히, 좁으면 위아래로 배치한다 (`PLOT_WIDE_RATIO`).

**축척은 미터, 눈금은 위경도.** 궤적을 놓는 좌표계는 플랫폼 기준 동–북 평면(미터)이지만,
축에 적는 값은 위도·경도(도)다. 둘을 섞는 이유는 각각 다른 일을 하기 때문이다.

- 평면을 **등축척(미터)** 으로 잡아야 궤적의 모양이 찌그러지지 않는다.
  위경도로 직접 그리면 위도 32°에서 경도 1°가 위도 1°보다 15% 짧은 것이 무시되어
  원이 타원으로 보인다.
- 눈금은 **위경도**여야 입력한 값과 바로 대조할 수 있다.
  "동쪽으로 1.5 km" 보다 "경도 126.03°" 가 설정 표의 값과 같은 단위다.

```c
// f_ComputeView (TrajectoryPlot.cpp:491)  — 축척은 미터로
pixelPerMeter = fmin(width / spanEast, height / spanNorth);    // 둘 중 작은 쪽

// 눈금 간격은 축마다 따로, 도 단위로
f_PlotToLla(centerEast - halfEast, centerNorth, &st_Low);      // 보이는 왼쪽 끝의 경도
f_PlotToLla(centerEast + halfEast, centerNorth, &st_High);     // 오른쪽 끝의 경도
gridLonDeg = f_Plot_NiceStep(f_Rad_To_Deg(st_High.lon - st_Low.lon), ...);
```

`f_Plot_NiceStep` (`:106`) 은 `{1, 2, 5} × 10^k` 중 눈금이 정해진 개수 이하가 되는 가장 작은
간격을 고른다 — 축 눈금이 `0.0137°` 같은 값이 되지 않게 하는 표준 기법.

**축마다 따로 잡는 이유** — 위경도는 축에 따라 도당 미터가 다르고(위도 32°에서
경도 1° = 94.3 km, 위도 1° = 110.9 km), 라벨 폭도 다르다. `126.05` 는 세로선 사이에
가로로 들어가야 하고 `32.10` 은 가로선 사이에 세로로 들어간다. 그래서 눈금 개수 상한을
축의 픽셀 크기와 라벨 크기로 각각 제한한다 (`PLOT_LON_LABEL_PX` 78, `PLOT_LAT_LABEL_PX` 34).
창이 좁아지면 경도 눈금이 먼저 성글어져 라벨이 겹치지 않는다.

**격자선 자리 잡기** — 눈금 값(도)을 다시 평면 좌표로 되돌려 픽셀을 구한다.
`f_LlaToPlot` (`:573`) 이 `f_PlotToLla` (`:548`) 의 역이며, 둘 다 좌표 라이브러리의
공개 함수만 쓴다 (`f_Trans_Lla_To_Ecef` ↔ `f_Trans_Ecef_To_Lla`,
`f_Trans_Ecef_To_Ned` ↔ `f_Trans_Ned_To_Ecef`). 접평면 근사라 왕복 오차가 남지만
11 km 거리에서 1.7 cm 로 화면 한 픽셀의 수백분의 일이다.

**끌어서 편집** — 그림에서 표적 시작점을 끌면 초기 위경도가 바뀐다.
이때 **화면 좌표 → LLA 는 `f_ComputePoints` 의 정확한 역경로**를 탄다.

```
픽셀 → (east, north) → NED → f_Trans_Ned_To_Ecef (회전 + 기준점 더하기) → f_Trans_Ecef_To_Lla
```

여기서 `f_Trans_Ned_To_Ecef`(점 변환, 기준점 포함)를 쓴다. 4.5절의 구분이 실제로
쓰이는 자리다.

**`WM_NOTIFY` 네 종** (`TrajectoryPlot.h:6-9`) 으로 대화상자에 알린다:
`PLOTN_SELECT` / `PLOTN_MOVE` / `PLOTN_TURN` / `PLOTN_SCRUB`.
그림은 모델을 직접 고치지 않는다.

## 6.7 대화상자 — 자동 실행과 재생

### 자동 실행 — `f_ScheduleRun` (`TargetSimUIDlg.cpp:1505`)

**[실행] 버튼이 없다.** 값을 고치면 자동으로 다시 돈다.

```c
isResultStale = 1;                       // 화면 결과가 지금 입력과 다르다

// 빨리 끝나는 시나리오는 바로, 오래 걸리면 입력이 멎은 뒤에
if ((st_Result.f_GetSampleNum() == 0) || (st_Result.f_GetRunMs() < UI_FAST_RUN_MS))   // 40 ms
{
    f_RunScenario();
}
else
{
    isRunPending = 1;
    SetTimer(UI_RUN_TIMER_ID, UI_RUN_DELAY_MS, nullptr);    // 250 ms 디바운스
}
```

**직전 실행 시간을 보고 전략을 고른다.** 명세 시나리오(2.3 ms)는 즉시,
최악 부하(0.8 s)는 입력이 멎은 뒤 한 번. 사용자가 ▲ 를 연타해도 실행이 쌓이지 않는다.

`isResultStale` 플래그가 중요하다 — 실행에 실패하면 화면에는 **마지막으로 성공한 결과**가
남아 있는데, 그 상태에서 CSV 를 저장하면 입력과 다른 결과가 저장된다.
그래서 저장 시 경고 문구를 붙이고 기동 구간 띠의 현재 시각 선을 숨긴다.

### 재생 — `OnTimer` (`:1950`)

100 ms 타이머로 슬라이더를 움직인다. 배속 x1~x100 (`s_PlaySpeed`).

`syncSource` 인자로 **부른 쪽 컨트롤은 건드리지 않는다** —
슬라이더에서 왔으면 슬라이더를 다시 세팅하지 않는다. 무한 루프 방지.

### 배치 — `f_Layout` (`:374`)

|---|---|---|

**해석**
- 대함은 Yaw 270° = 항상 정서 → 평행권(같은 위도선)을 따라간다.
  평행권 반경 `r = (N+h)·cos φ = 5,406,700 m`, `Δλ = −1800/r = −0.0190749°`
  → `126.03 − 0.019075 = 126.010925°`. **닫힌 식과 9자리까지 일치한다.**
- 대공은 Yaw 180° = 정남 → 자오선을 따라간다. 고도 300 m 를 반영해
  `(M+h)` 로 수치적분하면 32.011788° — **실측과 일치**.
  고도를 빼먹고 `s/M` 으로 계산하면 32.011784° 로 **0.57 m 어긋난다.**

> ⚠ **거리로 검증할 때의 함정** — 시작·끝 위경도로 잰 **지표면** 측지선은 대공 표적에서
> 12,000 m 가 아니라 **11,999.433 m** 다. 300 m 위를 날았으므로 `(1 + h/M) = 1.0000472`
> 를 곱해야 12,000.000 m 가 된다. 고도와 무관한 기준이 필요하면 위 표처럼
> **스텝마다 움직인 ECEF 거리의 합**을 쓴다.

# 10. 알려진 한계

**설계상 한계 (의도적)**

1. **짐벌락** — 자세를 roll/pitch/yaw 로 직접 적분하므로 pitch 가 ±90° 근처면
   yaw 축이 진행 방향과 겹쳐 yaw 기동이 궤적을 바꾸지 못한다 (`TargetSim_JH.c:314`).
   쿼터니언이면 없어지지만 명세가 자세를 오일러각으로 규정했다.
   UI 가 pitch 를 ±90° 로 제한해 완화한다 (`SCN_PITCH_LIMIT`).
2. **기동 겹침 거부** — 합성 규칙이 명세에 없으므로 실행 전에 반려한다.
3. **자전·중력·대기 없음** — ECEF 를 관성계처럼 쓴다. 60초·12 km 규모에서는
   코리올리 효과가 무시할 수준이고, 명세도 요구하지 않는다.
4. **자오선 수렴** — Yaw 를 "그 지점의 북쪽" 기준으로 재므로, 표적이 동서로 움직이면
   그 북쪽이 조금씩 돌아간다. 1G 선회의 원 맞춤 반경이 `V²/(n·g)` 보다
   위도 32°에서 1.4 m(0.034%) 작게 나오는 원인이다. **적분 오차가 아니라 모델의 성질**이며,
   적도에서는 +0.004 m, 위도 60°에서는 −3.8 m 로 `tan(위도)` 에 비례한다.

**구현상 한계**

5. **Core 는 비유한 값을 걸러 내지 않는다.** 표적 속력·기동 시각·G·LLA·자세에
   NaN/Inf 를 넣으면 `TGT_OK` 로 통과한다. UI 입력 단계(`f_Num_Parse`)에서만 막는다.
   Core 를 다른 곳에 붙일 때 주의할 점.
6. **UI 스레드에서 동기 실행.** 최악 부하에서 값을 고칠 때마다 0.7~0.8 s (Debug 2.8 s)
   입력이 멈춘다. 진행 표시·취소가 없다. 40 ms / 250 ms 기준은 명세에 없는 판단.
7. **되돌리기(Undo) 없음.** Esc 는 열려 있는 칸만 되돌린다. 삭제는 확인 없이 즉시.
8. **그림에서 끌어 놓은 위치는 접평면 근사**다. 고도가 높은 표적은
   `(1 + h/R)` 만큼 어긋난다 (15 km 거리·고도 3000 m 에서 약 7 m, 화면에서 1 px 미만).
9. **DPI 는 시스템 배율만 따른다** (모니터별 배율 미지원).
10. **명세 3-(4) "시뮬레이션 결과 설명" 미착수.** 출력물(CSV, 그림 파일)도
    저장소에 없다. 정정기록 2-C·4절의 수치를 그대로 쓸 수 있다.

## 11.2 스스로 확인해 볼 실험

각각 "예상을 먼저 적고 → 돌려 보고 → 다르면 왜 다른지 찾는다".

1. **속력 보존** — 명세 시나리오를 돌려 전 구간 `|V_ecef|` 의 표준편차를 재라.
   0 이어야 한다. **왜 0 인가?** (→ 3.3 결정 2, 4.3절)
2. **Roll 실험** — 대공 표적에 Roll 2G 를 0~60초 걸고, 기동 없는 경우와
   CSV 를 비교하라. 위경고도가 **모든 행에서 동일**해야 한다.
   **왜 그런가?** (→ 5.5절 마지막)
3. **수렴 차수** — 1G Yaw 선회를 Δt = 0.1 / 0.05 / 0.025 로 세 번 돌려
   끝 위치 오차 비를 보라. 0.25 가 나와야 한다.
   **0.5 가 나온다면 코드 어디가 잘못된 것인가?** (→ 5.6절 ⚠)
4. **경계 한 스텝** — 기동 A `[0,20)`, B `[20,40)` 을 넣고 t = 20.0 의 자세각을 보라.
   A 의 각속도인가 B 의 것인가? **`TGT_TIME_EPSILON` 을 0 으로 바꾸면 어떻게 되는가?**
5. **자오선 수렴** — 200 m/s 1G 선회를 위도 0° / 32° / 60° 에서 각각 돌려
   궤적에 원을 맞춰 반경을 재라. `V²/(n·g) = 4078.9 m` 와의 차이가
   `tan(위도)` 에 비례하는가? **적분 오차가 아니라는 근거는?** (→ 10절 4)
6. **시각 누적 vs 곱셈** — `f_Tgt_StepSim` 의 `curTime` 을 `+= stepTime` 누적으로
   바꿔 600 스텝 뒤 `simTime` 을 찍어 보라. 60.0 이 나오는가?
7. **중점 위치 제거** — `f_Tgt_Propagate` 의 ⑤ 를 지우고 ⑥ 에서
   `st_State->st_Lla` 를 쓰도록 되돌린 뒤, 실험 3 을 다시 하라.
   **비가 0.25 에서 얼마로 바뀌는가? 수평 비행 고도는?**
8. **극점** — 위도 89.8°, Yaw 0°(북), 200 m/s 로 60초 돌려 보라.
   무슨 일이 일어나며, 코드 어디가 그것을 처리하는가? (→ 4.4절 3)

## 11.3 "코드로 설명하라"(명세 3-(3)) 요구에 답하는 3분 스크립트

> 표적은 **속력 숫자 하나와 자세각**으로 정의됩니다. 속도 벡터는 저장하지 않고
> `f_Tgt_GetVelEcef` 가 매번 `(V,0,0)` 을 **자세로 한 번, 위경도로 한 번** 돌려 만듭니다.
> 두 번 돌리는 이유는 "남쪽" 이 지구 위 어디에 서 있느냐에 따라 다른 방향이기 때문입니다.
> 회전 행렬은 크기를 바꾸지 않으므로 **속력은 구조적으로 보존됩니다** — 실측 변동폭이
> 1e-14 m/s 입니다.
>
> 기동은 위치를 직접 건드리지 않습니다. `f_Tgt_GetAttRate` 가 `[start, end)` 구간에서
> `ω = n·g/V` 를 계산해 TurnType 이 지정한 축의 각속도로 넣고, 자세가 바뀌면
> 다음 스텝의 속도 **방향**이 바뀌어 궤적이 휩니다. Roll 은 동체 x 축 둘레의 회전이라
> `(V,0,0)` 을 바꾸지 못해 궤적이 그대로 — 특별 처리 없이 수학이 그렇게 만듭니다.
>
> 적분은 `f_Tgt_Propagate` 의 **중점법**입니다. 속도가
> `C(위경도)·C(자세)·(V,0,0)` 이므로 한가운데 방향을 얻으려면 **한가운데 자세와
> 한가운데 위치가 둘 다** 필요합니다. 처음에는 자세만 중점값을 써서 1차로 떨어졌고,
> Δt 를 절반으로 줄여 오차 비를 보는 검사(0.25 여야 함)에서 0.47 이 나와 발견했습니다.
> 고친 뒤 Δt 0.1 에서 위치 오차 0.008 m, 절반 비 정확히 0.250 입니다.

## B.4 주요 공식

```
프라임 수직 곡률반경   N(φ) = a / √(1 − e²sin²φ)
LLA → ECEF            x = (N+h)cosφ cosλ
                      y = (N+h)cosφ sinλ
                      z = (N(1−e²)+h) sinφ

속도 변환             V_ecef = C_ned→ecef(φ,λ) · C_body→ned(roll,pitch,yaw) · (V,0,0)ᵀ

기동 각속도           ω = n·g / V
선회 반경             R = V² / (n·g)
선회 주기             T = 2π·V / (n·g)
스텝당 회전각         Δψ = ω·Δt = n·g·Δt / V

중점법                att_mid = att_k + rate·(Δt/2)
                      P_mid   = P_k + V(att_k, LLA_k)·(Δt/2)
                      P_k+1   = P_k + V(att_mid, LLA(P_mid))·Δt
                      att_k+1 = wrap(att_k + rate·Δt)

Euler 오차 (선회)     최대 V·Δt  (원 중심이 V·Δt/2 만큼 밀림)
중점법 오차 차수      O(Δt²)  → Δt 절반이면 오차 1/4
```
