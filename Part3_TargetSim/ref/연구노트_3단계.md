# 연구 노트 — 과제 3 / 3단계

# 3단계 : 시뮬레이션 실행기

## 3-1. 목적

2단계에서 만든 것은 **"표적 하나를 0.1초 앞으로 보내는"** 함수 하나였다.
과제가 요구하는 것은 **"플랫폼과 표적 여러 개를 60초 동안 600번 움직이고 그 기록 601개를 남기는 것"** 이다.

이 둘 사이를 메우는 계층이 3단계다.

결과물 : `TargetSimCore/include/TargetSim_JH.h` (구조체·함수 추가)
         `TargetSimCore/src/TargetSim_JH.c` (실행기 구현 추가)

---

## 3-2. 왜 별도 계층이 필요한가

2단계 함수 `f_Tgt_StepTarget()` 은 아는 것이 적다.

- 표적 **하나만** 안다. 플랫폼도 다른 표적도 모른다
- **지금이 몇 번째 스텝인지** 모른다
- **언제 끝나는지** 모른다

이 정보를 UI 쪽에 두면 두 가지 문제가 생긴다.

1. Core 만 따로 테스트할 수 없다 (UI 를 띄워야만 확인 가능)
2. 나중에 다른 UI(콘솔·웹 등)를 붙이면 같은 로직을 또 짜야 한다

그래서 **Core 안에 시뮬레이션 진행을 담당하는 계층** 을 하나 더 두었다.

```
[3단계] 시뮬레이션 실행기 : 몇 번째 스텝인가, 표적이 몇 개인가, 언제 끝나는가
              ↓ 호출
[2단계] 궤적 모의 엔진    : 표적 하나를 dt 만큼 앞으로
              ↓ 호출
[공통]   좌표변환·행렬     : LLA ↔ ECEF, DCM
```

## 3-3. 새로 만든 구조체 2개

### (1) `ST_SimSample` — "한 장의 사진"

어떤 한 시각에 플랫폼과 모든 표적이 어디에 어떤 자세로 있는지를 통째로 담은 것이다.
시간을 멈추고 찍은 스냅사진이라고 보면 된다.

```c
typedef struct
{
    FLOAT64         simTime;                         // [s] = nStepIndex * stepTime
    INT32           nStepIndex;                      // 0 ~ nStepNum
    INT32           nTargetNum;
    ST_TargetState  st_Platform;
    ST_TargetState  st_Target[TGT_MAX_TARGET_NUM];   // nTargetNum 이후 칸은 0
} ST_SimSample;
```

**플랫폼과 표적이 같은 `ST_TargetState` 타입을 쓴다.** 플랫폼도 "속도 0, 기동 없는 표적"
으로 보면 되므로 따로 만들 이유가 없다. 나중에 표·그림·CSV 에서 똑같이 다룰 수 있다.

### (2) `ST_SimState` — "촬영 진행 상황"

사진을 찍는 사람이 들고 있는 메모장이다. 총 몇 장을 찍어야 하는지, 지금 몇 장째인지,
어떤 설정으로 찍는 중인지를 기억한다.

```c
typedef struct
{
    INT32         nStepNum;      // 전체 스텝 수. 표본 수는 nStepNum + 1
    ST_SimSample  st_Sample;     // 가장 최근 표본
    ST_SimConfig  st_Config;     // 설정의 사본
} ST_SimState;
```

### 크기 (x64 실측)

| 구조체 | 크기 |
|---|---|
| `ST_TargetState` | 104 B |
| `ST_SimSample` | 1,160 B (= 8 + 4 + 4 + 104 + 104 × 10) |
| `ST_SimConfig` | 10,320 B |
| `ST_SimState` | 11,488 B |

## 3-4. 새로 만든 함수 2개

```c
EN_TgtStatus f_Tgt_InitSim(ST_SimState *st_Sim, const ST_SimConfig *st_Config);
EN_TgtStatus f_Tgt_StepSim(ST_SimState *st_Sim);
```

사용 흐름은 이렇다.

```
1) 설정을 채운다                     (표적 2개, 60초, 0.1초)
2) f_Tgt_InitSim()  호출             → 검증 + t=0 상태 생성
3) 첫 표본(t=0)을 저장
4) f_Tgt_StepSim() 을 600번 반복      → 매번 0.1초씩 전진
   호출할 때마다 st_Sim->st_Sample 을 배열에 복사해 저장
5) 표본 601개 완성
```

**왜 601개인가** : t = 0, 0.1, 0.2, ... , 60.0 이므로 **스텝은 600번, 사진은 601장** 이다.
전봇대를 600칸 간격으로 세우면 전봇대는 601개인 것과 같다.

## 3-5. 설계 판단 ① 스텝 수 계산과 "정수배" 강제

### 공식

```
ratio    = durationTime / stepTime
nStepNum = round(ratio)            // floor(ratio + 0.5)

조건 : |ratio − nStepNum| ≤ 1e-6      (정수배여야 함)
       stepTime  ≥ 0.001 s           (TGT_MIN_STEP_TIME)
       nStepNum  ≤ 100,000           (TGT_MAX_STEP_NUM)
```

과제 시나리오는 `60.0 / 0.1 = 600` 이므로 스텝 600회, 표본 601개다.

### 왜 정수배를 요구하는가

정수배가 아니면 마지막 스텝이 어중간해진다.

| duration / step | ratio | 판정 |
|---|---|---|
| 60.0 / 0.1 | 600.000000 | 통과 |
| 60.0 / 0.3 | 200.000000 | 통과 |
| 1.0 / 0.3 | 3.333333 | **거부** |
| 60.0 / 0.007 | 8571.428571 | **거부** |

`1.0 / 0.3` 이면 3번 진행하면 0.9초, 4번 진행하면 1.2초라 정확히 1.0초에 멈출 수 없다.
"마지막 스텝만 0.1초로 짧게" 같은 예외를 만들면 코드가 복잡해지고 설명도 어려워진다.
**입력 단계에서 거부하는 쪽이 훨씬 단순하고 결과 설명도 명확하다.**

### 비교를 "긍정형"으로 쓴 이유 — NaN 방어

코드는 `stepTime >= TGT_MIN_STEP_TIME` 처럼 **"~ 이상이면 통과"** 형태로 썼다.
`stepTime < TGT_MIN_STEP_TIME` (거부 조건)으로 쓰지 않았다.

이유는 **NaN(Not a Number, 숫자가 아님)** 때문이다.
0 을 0 으로 나누는 등 계산이 깨지면 NaN 이 나오는데, NaN 은 **어떤 비교를 해도 전부 거짓** 이다.

```
NaN >= 0.001  →  거짓
NaN <  0.001  →  거짓
```

거부 조건으로 쓰면 NaN 이 "거부 조건에 안 걸렸으니 통과" 가 되어 그대로 흘러 들어간다.
통과 조건으로 쓰면 NaN 은 자동으로 거부된다.

### 실수 → 정수 변환 전에 범위를 먼저 확인

C 언어에서 **표현 범위를 넘는 실수를 정수로 바꾸면 무슨 값이 나올지 정해져 있지 않다**
(미정의 동작). 그래서 `(INT32)nearest` 로 바꾸기 **전에** `nearest ≤ 100000` 을 먼저 확인한다.

## 3-6. 설계 판단 ② 시각을 "누적"하지 않고 "곱한다"

### 문제 : 0.1 은 컴퓨터가 정확히 저장할 수 없다

컴퓨터는 수를 2진법으로 저장한다. 10진수 0.1 은 2진법으로 쓰면 **무한소수** 라서
정확히 담기지 않는다. 실제로 저장되는 값은 이렇다.

```
0.1  →  0.10000000000000000555...
```

10진법에서 1/3 을 0.3333... 으로 끝없이 써야 하는 것과 같은 상황이다.

### 그래서 더하면 오차가 쌓인다

```
방식 A (누적)  :  t = t + 0.1  을 600번
방식 B (곱셈)  :  t = 600 × 0.1  을 1번
```

실제 계산 결과다.

| 방식 | 600스텝 후 값 | 참값과의 오차 |
|---|---|---|
| 누적 | 60.00000000000058265 | 5.8 × 10⁻¹³ s |
| 곱셈 | 60.00000000000000000 | 0 |

누적은 오차가 **600번 쌓인다.** 곱셈은 **한 번만** 일어난다.

### 그래서 코드는 이렇게 한다

```c
curTime  = (FLOAT64)nStepIndex * stepTime;
nextTime = (FLOAT64)(nStepIndex + 1) * stepTime;
```

시각을 변수에 더해 나가지 않고, **스텝 번호에 간격을 곱해서** 매번 새로 만든다.
스텝 번호는 정수라 오차가 전혀 없다.

**왜 중요한가** : 60초 시뮬레이션이 60.0000000000006초에서 끝나면
"마지막 스텝인가?" 판정이 어긋날 수 있고, 기동 종료 시각 비교도 틀어진다.

## 3-7. 설계 판단 ③ 기동 경계에 아주 작은 여유(1e-6)를 준다

곱셈으로 바꿔도 **완전히** 정확해지지는 않는다. 간격이 0.3초인 경우를 보자.

```
3 × 0.3 = 0.89999999999999991      ← 10진수 0.9 보다 아주 조금 작다
```

만약 `startTime = 0.9` 인 기동이 있고, 조건을 `startTime <= simTime` 으로 쓰면
`0.9 <= 0.89999999999999991` 은 **거짓** 이 되어 **기동이 한 스텝 늦게 시작한다.**

그래서 판정할 때 아주 작은 여유를 더한다.

```c
evalTime = simTime + TGT_TIME_EPSILON;      // TGT_TIME_EPSILON = 1e-6
```

### 1e-6 이 적당한 이유

```
관측된 최대 반올림 오차   ≈ 5.8 × 10⁻¹³ s
여유값                    =  1.0 × 10⁻⁶ s     ← 오차보다 약 170만 배 크다 (충분히 덮는다)
스텝 간격                 =  1.0 × 10⁻¹ s     ← 여유값보다 10만 배 크다 (기동을 앞당기지 않는다)
```

**너무 작으면 반올림 오차를 못 덮고, 너무 크면 기동이 한 스텝 일찍 시작해 버린다.**
1e-6 은 그 사이에서 양쪽 모두 안전한 값이다.

## 3-8. 설계 판단 ④ 기동 구간을 반열린 구간 `[start, end)` 으로 본다

### 반열린 구간이란

- `[` 는 **포함**, `)` 는 **불포함** 을 뜻한다
- `[0, 30)` 은 0초는 포함하고 30초는 포함하지 않는다는 뜻

### 왜 이렇게 하는가

기동 A 가 `[0, 30)`, 기동 B 가 `[30, 60)` 이면 **30초를 아무도 중복해서 쓰지 않는다.**
30초는 오직 B 만의 것이다. 그래서 **연속된 기동을 빈틈도 겹침도 없이 이어 붙일 수 있다.**

만약 양쪽 다 포함(`[0, 30]`, `[30, 60]`)으로 하면 30초에 두 기동이 동시에 유효해져
"겹침 금지" 규칙에 걸려 버린다.

### 겹침 판정식

두 구간 A = `[a1, a2)`, B = `[b1, b2)` 가 겹치는 조건은 다음 한 줄이다.

```
(a1 < b2) 이고 (b1 < a2)
```

**왜 이 식인가** : 겹치지 **않는** 경우는 두 가지뿐이다.

```
경우 1 : A 가 B 보다 완전히 앞  →  a2 ≤ b1
경우 2 : B 가 A 보다 완전히 앞  →  b2 ≤ a1
```

이 둘 중 아무것도 아니면 겹친 것이다. 부정하면 `a2 > b1` 이고 `b2 > a1`,
즉 `b1 < a2` 이고 `a1 < b2` 가 된다.

부등호가 `<` (등호 없음)이므로 `a2 == b1` (끝과 시작이 같음)은 겹침이 아니다. 의도한 대로다.

## 3-9. 설계 판단 ⑤ 플랫폼도 표적과 똑같은 길을 지난다

플랫폼은 기동이 없고 이번 과제에서는 속도도 0 이다. 그래도 **따로 코드를 만들지 않았다.**

```c
// 각속도를 전부 0 으로 채워서 표적과 같은 적분 함수를 부른다
st_Rate.roll = 0.0;  st_Rate.pitch = 0.0;  st_Rate.yaw = 0.0;
f_Tgt_Propagate(st_State, &st_Rate, st_Platform->headingSpeed, stepTime, nextTime);
```

**장점** : 코드가 한 벌뿐이라 고칠 곳도 한 곳이고, 플랫폼이 움직이는 시나리오로 확장해도
그대로 동작한다.

### 속도 0 이 안전한 이유

2단계 각속도 공식은 속도로 나눈다.

```
ω = n · g / V          ← V 가 0 이면 0 으로 나누기
```

그런데 **플랫폼 경로에서는 이 식을 아예 지나지 않는다.** 각속도를 계산하지 않고 0 을 바로 넣기 때문이다.
적분 경로(`f_Tgt_Propagate`)에는 속도로 나누는 연산이 없으므로 V = 0 이어도 문제없다.

그래서 검증 규칙이 이렇게 갈린다.

| 대상 | 속도 조건 | 이유 |
|---|---|---|
| 플랫폼 | `V ≥ 0` | 정지 허용 |
| 표적 | `V > 0` | 각속도 식의 분모라 0 이면 안 됨 |

## 3-10. 설계 판단 ⑥ 설정을 "사본" 으로 들고 있는다

`ST_SimState` 는 `ST_SimConfig` 를 **포인터가 아니라 값으로** 가지고 있다.

```c
st_Sim->st_Config = *st_Config;      // 통째로 복사
```

**이유** : UI 에서 시뮬레이션을 시작한 뒤 사용자가 화면의 숫자를 바꿔도,
**진행 중인 시뮬레이션이 중간에 흔들리면 안 되기 때문이다.**

포인터로 들고 있으면 사용자가 표적 수를 2개에서 5개로 바꾸는 순간
300번째 스텝부터 표적이 5개가 되어 버린다. 결과가 뒤죽박죽이 된다.

사본을 만드는 대가는 메모리 10 KB 인데, 결과의 일관성이 훨씬 중요하다.

## 3-11. 설계 판단 ⑦ 매 스텝마다 다시 검증한다

`f_Tgt_StepSim()` 은 **호출될 때마다** 아래를 전부 다시 확인한다.

1. 설정이 여전히 유효한가 (`f_Tgt_ValidateConfig`)
2. 스텝 수가 설정과 일치하는가
3. 현재 스텝 번호가 0 ~ nStepNum 범위 안인가
4. 표본의 표적 수가 설정의 표적 수와 같은가

"초기화 때 한 번 확인했으면 됐지 왜 매번 하나?" 싶지만 이유가 있다.

`ST_SimState` 는 **공개 구조체** 라서 호출하는 쪽이 멤버를 직접 건드릴 수 있다.
누가 실수로 `nStepIndex` 를 음수로 바꾸거나 `nTargetNum` 을 15 로 바꾸면
**배열 범위 밖을 읽거나 쓰게 되고, 그것은 프로그램이 통째로 망가지는 종류의 사고다.**

MISRA C 규칙(Dir 4.1, Rule 18.1)도 **"배열 인덱싱과 나눗셈은 안전하다는 근거를 그 자리에서
세울 수 있어야 한다"** 고 요구한다. 매번 확인하는 것이 그 근거다.

확인 비용은 표적 10개 기준 수십 번의 비교뿐이라 600 스텝 전체에서도 무시할 수준이다.

## 3-12. 설계 판단 ⑧ 사본에서 다 진행한 뒤 한 번에 반영한다

```c
st_Next = st_Sim->st_Sample;         // 1) 통째로 복사

... 플랫폼과 표적을 전부 진행 ...      // 2) 사본 위에서만 작업

if (enStatus == TGT_OK)              // 3) 전부 성공했을 때만
{
    st_Sim->st_Sample = st_Next;     //    한 번에 바꿔치기
}
```

**이유 1** : 표적 3개 중 2번째에서 좌표 변환이 실패하면, 사본을 안 쓸 경우
**1번 표적은 0.2초, 2·3번 표적은 0.1초** 인 뒤죽박죽 상태가 남는다.
사본을 쓰면 실패 시 원래 상태가 그대로 보존된다.

**이유 2** : 한 표본 안의 모든 물체가 **정확히 같은 시각** 을 갖는다.

은행 송금이 "전부 성공하거나 전부 취소" 되는 것과 같은 원리다.

## 3-13. 쓰지 않는 표적 칸을 0 으로 채운다

배열은 항상 10칸이지만 실제로는 2개만 쓴다. 나머지 8칸은 `f_Tgt_ClearState()` 로
전부 0 으로 채운다.

**이유** : 초기화하지 않은 메모리에는 **이전에 다른 프로그램이 쓰던 쓰레기 값** 이 남아 있다.
실수로 그 칸을 읽으면 말도 안 되는 좌표가 표나 그림에 나타나고, 원인 찾기가 매우 어렵다.

## 3-15. 호출하는 쪽(UI)에서의 사용

```
1) f_Tgt_InitSim(&st_Sim, &st_Config)
2) 표본 배열을 nStepNum + 1 개만큼 확보
3) 배열[0] = st_Sim.st_Sample                     ← t = 0 저장
4) for (n = 1; n < 표본수; n++)
       f_Tgt_StepSim(&st_Sim)
       배열[n] = st_Sim.st_Sample
5) 실패하면 몇 번째 스텝에서 왜 실패했는지 표시하고, 이전 결과는 그대로 둔다
```

### 필요한 메모리

| 조건 | 표본 수 | 메모리 |
|---|---|---|
| 60초 / 0.1초 (과제) | 601 | 0.66 MB |
| 60초 / 0.01초 | 6,001 | 6.6 MB |
| 상한 (100,000 스텝) | 100,001 | 110.6 MB |

(여기서 1 MB = 1,048,576 바이트다. 1 MB = 1,000,000 바이트로 세면 0.70 / 6.96 / 116.0 MB 이고,
4단계 노트에 나오는 "116 MB" 가 이 세 번째 값과 같은 것이다.)

과제 조건에서는 1 MB 도 안 되므로 전혀 부담이 없다.
다만 상한까지 가면 110 MB 이므로, UI 는 메모리 확보에 실패하면
**필요한 용량을 MB 단위로 알려 주고 실행을 중단한다.**

> 참고 : Core 는 MISRA 규칙에 따라 동적 할당을 쓰지 않지만,
> **UI(C++/MFC)는 MISRA C 적용 대상이 아니므로** 표본 버퍼는 UI 쪽에서 할당한다.
> Core 는 "가장 최근 표본 한 장" 만 들고 있고, 601장을 쌓는 것은 호출자의 몫이다.
> 이렇게 나누면 Core 의 메모리 사용량이 설정과 무관하게 고정된다.

## 3-17. 정리 — 3단계에서 내린 판단 8가지

| # | 판단 | 근거 |
|---|---|---|
| 1 | 스텝 수는 나눗셈 + 반올림, 정수배만 허용 | 마지막 스텝이 어중간해지는 것을 막음 |
| 2 | 시각은 누적하지 않고 스텝 번호 × 간격 | 부동소수 오차가 600번 쌓이는 것을 막음 (5.8e-13 → 0) |
| 3 | 기동 경계 판정에 1e-6 여유 | 곱셈도 완전히 정확하진 않음 (3 × 0.3 = 0.8999...) |
| 4 | 기동 구간은 반열린 구간 `[start, end)` | 연속 기동을 빈틈·겹침 없이 이어 붙이기 위해 |
| 5 | 플랫폼도 표적과 같은 적분 경로 | 코드 중복 제거, 확장성. 각속도 0 이라 V=0 도 안전 |
| 6 | 설정을 사본으로 보관 | 실행 중 설정이 바뀌어도 결과가 흔들리지 않음 |
| 7 | 매 스텝 재검증 | 공개 구조체라 외부에서 망가뜨릴 수 있음 (MISRA Dir 4.1 / 18.1) |
| 8 | 사본에서 진행 후 한 번에 반영 | 실패 시 이전 상태 보존, 한 표본의 시각 일관성 |

## 3-18. 남은 확인 사항
