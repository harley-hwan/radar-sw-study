## 목적

1. 과제 명세 2절 "시뮬레이션 조건" 의 실행 부분을 Core 에 구현한다.
   설정(`ST_SimConfig`) 하나로 플랫폼과 표적 전체를 0 ~ durationTime 동안 stepTime 간격으로 전파한다 (명세 조건 60 s / 0.1 s, 표본 601개).
2. 2단계 엔진으로는 전파할 수 없던 정지 플랫폼(0 m/s)을 전파한다.
3. 4단계 UI 가 결과(LLA 표·파일)와 5단계 그림에 그대로 쓸 수 있는 형태로 표본을 내준다.

## 방법

### API

| 항목 | 내용 |
|---|---|
| `f_Tgt_InitSim(ST_SimState *st_Sim, const ST_SimConfig *st_Config)` | 설정 검증, 스텝 수 계산, 설정 사본 저장, t = 0 표본 생성 |
| `f_Tgt_StepSim(ST_SimState *st_Sim)` | 플랫폼과 표적 전부를 한 스텝 전진 |
| `ST_SimSample` (1,160 B) | simTime, nStepIndex, nTargetNum, 플랫폼 상태, 표적 상태 10칸 (설정과 같은 인덱스, 빈 칸은 0) |
| `ST_SimState` (11,488 B) | nStepNum, 가장 최근 표본, 설정 사본 |
| 새 상태 코드 | `TGT_ERR_SIM_STATE` (맞지 않는 상태), `TGT_ERR_SIM_END` (마지막 표본 뒤 호출) |

### 설계

- **표본 보관**: Core 는 최근 표본 하나만 갱신하고, 호출자가 스텝마다 복사해 모은다.
  Core 는 malloc 을 쓸 수 없고, 표본 전체는 명세 조건만 해도 601 × 1,160 B ≈ 0.7 MB, 스텝 상한(표본 100,001개)에서는 약 116 MB 라 스택에 둘 수 없기 때문이다.
- **설정 사본**: 초기화 때 설정을 상태 안에 복사해, 초기화 뒤 원본 설정을 바꿔도 진행 중인 실행과 섞이지 않게 했다.
- **플랫폼 전파**: 2단계 `f_Tgt_StepTarget` 의 중점법 본체를 `f_Tgt_Propagate` 로 옮기고, 표적과 플랫폼이 함께 쓴다.
  - 플랫폼은 기동이 없어 각속도 0 으로 통과한다. 이 경로에는 속도로 나누는 연산이 없어 속도 0 이 안전하다.
  - 공개 `f_Tgt_StepTarget` 은 검사 후 같은 본체를 부르는 얇은 함수가 되었다 (부동소수 식은 그대로).
- **스텝 수** (`f_Tgt_GetStepNum`)
  - stepTime ≥ 1e-3 s, durationTime ≥ stepTime 일 때만 나눈다 (긍정형 비교라 NaN 도 걸린다).
  - ratio = durationTime / stepTime, nearest = floor(ratio + 0.5)
  - nearest ≤ 100,000 이고 |ratio − nearest| ≤ 1e-6 일 때만 INT32 로 변환한다 (범위 밖 변환은 미정의 동작).
  - 정수배가 아니면 거부한다 (`TGT_ERR_TIME`).
- **시각**: 누적(+=) 대신 `nStepIndex × stepTime` 으로 매기고, 종료 판정은 정수로만 한다.
  기동 판정도 표본 안의 객체 simTime 이 아니라 이 격자 시각으로 한다. ε = 1e-6 s 는 유지했다.
- **입력 검증 추가**: 검사 순서 NULL → 표적 수 → 시간(스텝 수) → 플랫폼 속도 → 표적별.
  플랫폼 속도는 `!((V >= 0.0) && (V < HUGE_VAL))` 이면 `TGT_ERR_SPEED` (0 허용, 음수·NaN·+Inf 거부).
- **원자성**: 지역 `ST_SimSample` 사본에서 플랫폼 → 표적 0 … 순서로 진행하고, 모두 성공했을 때만 한 번에 반영한다.
  초기화도 실패하면 상태에 아무것도 쓰지 않는다.
- **매 스텝 재검증**: `f_Tgt_StepSim` 은 공개 구조체가 호출 사이에 바뀔 수 있으므로 매번 설정 사본을 다시 검증하고,
  nStepNum·nStepIndex·nTargetNum 이 서로 맞는지 확인한다 (어긋나면 `TGT_ERR_SIM_STATE`).
- **규칙 대응**: Rule 10.8(합성 식 캐스트 금지), FLOAT64→INT32 범위 확인, Dir 4.11(나눗셈 분모), Rule 2.2(더미 초기화 금지),
  Rule 19.1(완전 겹침만 대입), MSVC C4701(값을 읽는 코드를 채운 호출과 같은 중첩 블록에 둠).

### 검증 방법

- 수정 착수 전 2단계 소스와 Debug/Release DLL 을 따로 보관해 기준으로 삼았다.
- 솔루션 밖 임시 하네스 4개 영역으로 나눠 검증했다: 회귀·시나리오 / 시간 규칙 / 견고성 / 정적 검사·코드 검토.
  - ε = 0 대조와 결함 주입은 Core 소스 **사본**을 고쳐 정적 빌드로 시험했다 (저장소 파일은 그대로).
- 검증에서 찾은 문제를 고친 뒤, 기존 하네스를 새 DLL 로 모두 다시 돌려 이전 출력과 비교했다.

### 검증 중 발견해 고친 것

- 새 플랫폼 속도 검사가 +Inf 를 통과시켜, 모든 호출이 `TGT_OK` 인데 플랫폼 표본이 NaN 이 되었다 → `< HUGE_VAL` 조건을 더해 거부.
- 주석 2건 정정: ε 주석의 "1 ulp"(누적 시각은 최대 23~77 ulp 차이), 헤더의 "LLA 는 출력용"(다음 스텝 NED 기준으로도 쓰임).
- 수정 후 재검증: 기존 하네스 출력 비교 94건(이전 출력·2단계 기준 대비 79건, 새 Release 대 Debug 15건) 중 달라진 것은 플랫폼 +Inf 관련 8건(판정표 +Inf 행·요약 줄, +Inf 관찰 줄, 각각 실행 조합 4개)뿐이고, 2단계 비트 회귀 덤프도 기준과 바이트 동일했다.

### 매 스텝 재검증 비용

- 최악 부하에서 스텝당 5.7 µs 중 재검증이 약 3.4 µs (58~60 %).
- 명세 시나리오(표적 2, 기동 0)에서는 재검증 1회 약 0.01 µs 로, 600 스텝 누계 0.01 ms 미만.

## 한계

- **입력 값의 물리적 타당성은 검사하지 않는다.**
  - 표적 속도 NaN·+Inf, gravityValue·위경도·자세의 비유한값은 `TGT_OK` 인 채 NaN 표본을 낸다 (2단계 검사를 그대로 둠).
  - 플랫폼 속도도 0 이상·유한만 보므로 1e308 m/s 같은 값은 통과해 첫 스텝부터 고도 +Inf 표본을 낸다.
  - → 4단계 입력 단계에서 막아야 한다.
- **`f_Tgt_StepSim` 이 잡지 못하는 변조**: 표본 안의 위치·자세·LLA 값, 빈 칸, 서로 맞게 함께 바꾼 설정·스텝 번호.
  → 호출자는 `f_Tgt_InitSim` / `f_Tgt_StepSim` 외에는 `ST_SimState` 에 쓰지 않는다.
- **호출자 계약**: 재초기화가 실패하면 이전 실행이 남아 `f_Tgt_StepSim` 으로 계속 진행된다.
  → 상태를 0 으로 채워 두고, `f_Tgt_InitSim` 이 실패하면 `f_Tgt_StepSim` 을 부르지 않는다.
- 매 스텝 전체 재검증이 최악 부하 스텝 시간의 약 60 % 를 차지한다.
- 스텝 수 상한 100,000, stepTime 하한 1e-3 s. durationTime 은 stepTime 의 정수배만 받는다 (허용 1e-6 스텝이라 60.0000001 s 도 600 스텝으로 수락).
- 격자 밖 기동 시각은 다음 격자로 밀린다. 격자 시각을 하나도 포함하지 않는 기동(예: 10.05~10.08 s)은 오류 없이 무시되고, 격자 시각을 포함하면 한 스텝보다 짧아도 한 스텝 전체에 적용된다(예: 10.1~10.15 s → 1 스텝).
- 정지 플랫폼은 표본 0(입력 LLA)과 표본 1 이후(역변환 LLA)의 고도가 −9.3e-10 m 다르다.
- `ST_SimState` 의 4 B 패딩은 Core 가 쓰지 않아, 상태 전체를 memcmp 로 비교하는 것은 0 으로 채운 상태에서만 의미가 있다.
- 시각이 2^34 s(약 1.7e10 s) 이상이 되는 설정(예: stepTime 1e10 s 에서 둘째 스텝 2e10 s 부터)에서는 t + 1e-6 이 t 로 반올림되어 ε 가 효과가 없다.
- 2단계가 커밋되지 않은 상태에서 3단계를 적용해, git 이력만으로는 두 단계의 변경을 나눠 볼 수 없다.
