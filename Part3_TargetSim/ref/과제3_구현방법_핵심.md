# (1) 표적 구조체 정의

## 표적 10개, 표적마다 기동 30개

명세가 "표적 개수를 설정할 수 있어야 한다(최대 10), 기동 횟수도 설정할 수 있어야 한다(최대 30)"고 했다.

배열을 **최대치로 미리 잡아두고, 지금 몇 개를 쓰는지를 숫자로 따로 적어두는** 방식으로 만들었다.

```c
ST_TargetInit       st_Target[10];   INT32 nTargetNum;      // 자리는 10개, 오늘은 2개만 사용
ST_TargetManeuver   st_Maneuver[30]; INT32 nManeuverNum;    // 자리는 30개, 오늘은 0개 사용
```

좌석 10개짜리 버스를 준비해 두고 "오늘 승객 2명"이라고 적어두는 것과 같다. 표적을 추가하거나 지울 때 자료구조를 다시 만들 필요 없이 `nTargetNum` 숫자만 바꾸면 된다. 시뮬레이션이 도는 동안 메모리 크기가 변하지 않으므로, 프로그램이 얼마나 메모리를 쓰는지가 시작부터 끝까지 똑같다.

빈 좌석은 0으로 채워둔다. 그러지 않으면 결과 표나 그림이 사용하지 않는 자리의 엉뚱한 값을 읽어서 화면에 이상한 숫자가 뜬다.

## 위치는 위도·경도·고도로, 속도는 동체 속도 하나로

명세에서 눈여겨볼 부분은 **속도를 숫자 하나(V_heading)로 받으라**는 것이다.

보통 속도는 (Vx, Vy, Vz) 세 개다. 그런데 명세는 하나만 준다. 그러면 방향은 어디에 있나? **자세각(Yaw·Pitch·Roll)이 갖고 있다.** 기수가 어디를 향하는지가 곧 진행 방향이다.

이 구조를 그대로 따라서 자료를 두 덩어리로 나눴다.

```c
// 사용자가 입력하는 값 — 처음에 정해지고 끝까지 안 변한다
typedef struct {
    ST_CoordLla  st_InitLla;      // 위도, 경도, 고도
    ST_CoordAtt  st_InitAtt;      // roll, pitch, yaw  ← 방향은 여기
    FLOAT64      headingSpeed;    // 속력 숫자 하나    ← 크기는 여기
    ...
} ST_TargetInit;

// 매 순간 변하는 값
typedef struct {
    FLOAT64      simTime;
    ST_CoordRect st_PosEcef;      // 계산은 여기서 한다
    ST_CoordRect st_VelEcef;
    ST_CoordLla  st_Lla;          // 화면 출력용
    ST_CoordAtt  st_Att;
} ST_TargetState;
```

### 속도 벡터를 저장해 두지 않고 매번 새로 만든다

여기가 이 설계에서 가장 중요한 선택이다.

흔한 방법은 속도 벡터 (Vx, Vy, Vz) 를 들고 있으면서 매 스텝 조금씩 회전시키는 것이다. 그런데 컴퓨터의 소수점 계산에는 아주 작은 오차가 따라붙는다. 회전을 600번 반복하면 그 오차가 쌓여서 **속력 자체가 조금씩 변한다.** 200 m/s 로 날던 표적이 199.98 m/s 가 되는 식이다. 표적이 선회한다고 해서 느려질 이유가 없는데도 그렇게 된다.

대신 "이 표적의 속력은 200"이라는 숫자를 붙박아 두고, 방향만 그때그때 자세각에서 꺼내 쓰면

```
속도 = 200 × (기수가 향하는 방향)
```

이 되어 **속력이 변할 수가 없다.** 몇 번을 회전시키든 200은 200이다. 나중에 검증할 때 확인해야 할 항목이 하나 줄어드는 셈이고, 실제로 명세 시나리오에서 60초 내내 정확히 30.000000 / 200.000000 이 나온다.

각도는 프로그램 안에서 전부 라디안으로 통일했다. 화면에서 도(°)로 받아 읽는 순간 라디안으로 바꾸고, 그 뒤로는 어디에도 도가 없다. 단위가 섞이면 어디서 틀렸는지 찾기가 매우 어려워진다.

## 기동 정보 네 가지

명세가 정해준 네 개를 그대로 담았다. 필드를 하나도 더 붙이지 않았다.

```c
typedef struct {
    EN_TurnType  enTurnType;     // 0 회전없음 / 1 Roll / 2 Yaw / 3 Pitch
    FLOAT64      gravityValue;   // 몇 G 로 도는가
    FLOAT64      startTime;      // 언제부터
    FLOAT64      endTime;        // 언제까지
} ST_TargetManeuver;
```

그런데 이 네 개만으로는 알 수 없는 게 세 가지 있다.

### ① 오른쪽으로 도나, 왼쪽으로 도나

방향을 담을 자리가 없다. 필드를 하나 더 만들 수도 있지만, 명세가 "네 가지를 포함하라"고 못박았으니 늘리고 싶지 않았다.

**G 값의 부호로 해결했다.** +2G 면 오른쪽, −2G 면 왼쪽. 크기와 방향을 숫자 하나가 같이 표현한다.

```
Roll  (+) 오른쪽으로 기울임     (−) 왼쪽으로 기울임
Yaw   (+) 오른쪽 선회           (−) 왼쪽 선회
Pitch (+) 기수 들어올림         (−) 기수 내림
```

### ② Roll 기동이 궤적을 바꾸나

TurnType 을 글자 그대로 **"어느 축을 돌리는가"** 로 해석했다.

- **Roll** — 비행기가 옆으로 기우는 것. 가는 방향은 그대로다. 궤적은 변하지 않고 자세만 변한다.
- **Yaw** — 수평면에서 도는 것. 위에서 보면 원을 그린다.
- **Pitch** — 위아래로 도는 것. 옆에서 보면 원을 그린다.

세 가지가 서로 대칭이라 코드가 `switch` 한 덩어리로 끝나고, 결과를 눈으로 확인하기도 쉽다.

### ③ 기동 시간이 겹치면

이건 뒤에 따로 설명한다.

# (2) 표적 상태 정보 갱신

## ECEF에서 갱신하라는 게 무슨 뜻인가

ECEF 는 지구 중심을 원점으로 하는 평범한 x·y·z 직교좌표다. 위도·경도와 달리 **그냥 더하면 되는** 좌표계다.

```
새 위치 = 이전 위치 + 속도 × 시간간격
```

위도·경도로 직접 계산하면 이렇게 간단하지 않다. 동쪽으로 1 m 갔을 때 경도가 얼마나 변하는지가 **위도마다 다르기 때문**이다. 적도에서는 경도 0.0000090° 지만 위도 60°에서는 0.0000180° 로 두 배다. 지구가 둥글어서 위로 갈수록 경도선 사이가 좁아지기 때문이다. 게다가 극점 근처에서는 아예 계산이 터진다.

그래서 **계산은 ECEF에서 하고, 위도·경도는 매 스텝 ECEF에서 다시 뽑아낸다.**

```
1. ECEF 위치 += ECEF 속도 × 0.1초
2. 그 ECEF 위치를 위도·경도·고도로 변환해서 같이 보관
```

2번을 매 스텝 하기 때문에, **ECEF → 위경도 변환이 부정확하면 궤적 전체가 부정확해진다.** 참고 소스의 변환 함수는 같은 계산을 5번 반복해서 근사하는 방식이었는데, 5번이 충분한지 보장이 없고 고위도에서는 고도가 크게 어긋났다. 반복 없이 한 번에 답이 나오는 **Bowring 공식**으로 바꿨다. 정확도는 밀리미터 수준이다.

## 동체 속도를 ECEF 속도로 바꾸기 — 명세의 "고민해보시오"

과제에서 "V_heading 을 ECEF 의 Vx, Vy, Vz 로 바꾸는 방법을 고민해보라"고 한 부분이다. 사실상 이 과제의 핵심이다.

### 한 번에 못 간다. 두 번 돌려야 한다

```
1단계   V_body = (200, 0, 0)                기수 방향으로 200 m/s
2단계   V_ned  = (자세각으로 회전) × V_body   북·동·아래 방향 성분으로
3단계   V_ecef = (위경도로 회전)  × V_ned     지구 좌표 성분으로
```

왜 두 번인지가 헷갈리기 쉬운데, 이렇게 생각하면 된다.

Yaw 180° 는 **"남쪽을 보고 있다"** 는 뜻이다. 그런데 "남쪽"이 지구 좌표로 어느 쪽인지는 **내가 어디에 서 있느냐에 따라 다르다.** 서울에서의 남쪽과 브라질에서의 남쪽은 우주에서 보면 완전히 다른 방향이다.

- 자세각(Yaw 180°)은 "내가 선 자리에서 남쪽" 이라는 **상대적인** 정보다.
- 그 자리가 지구 어디인지(위도 32°, 경도 126°)를 알아야 **절대적인** 방향이 나온다.

그래서 "자세에 의한 회전"과 "지구 위 위치에 의한 회전"을 따로 계산해서 이어 붙인다.

```c
static EN_CoordStatus f_Tgt_GetVelEcef(ST_CoordRect *st_VelEcef, const ST_CoordAtt *st_Att,
                                       const ST_CoordLla *st_Lla, FLOAT64 headingSpeed)
{
    st_VelBody.x = headingSpeed;  st_VelBody.y = 0.0;  st_VelBody.z = 0.0;

    enStatus = f_Trans_Body_To_Ned(&st_VelNed, &st_VelBody, st_Att);
    if (enStatus == COORD_OK) {
        enStatus = f_Trans_NedVec_To_Ecef(st_VelEcef, &st_VelNed, st_Lla->lat, st_Lla->lon);
    }
    return enStatus;
}
```

### 여기서 놓치기 쉬운 것

**두 번째 회전은 현재 위치에 따라 달라진다.** 표적이 움직였으면 회전 행렬도 다시 만들어야 한다. 처음 위치에서 만든 것을 계속 재사용하면, 이동한 거리만큼 지구가 휜 것을 무시하는 셈이 되어 오차가 그대로 쌓인다. 함수가 `st_Lla` 를 인자로 받는 이유가 이것이다.

**회전 행렬은 물체의 크기를 바꾸지 않는다.** 물건을 돌려도 길이가 변하지 않는 것과 같다. 그래서 200 m/s 를 두 번 돌려도 여전히 200 m/s 다. 앞에서 "속력이 구조적으로 보존된다"고 한 것이 여기서 완성된다.

**되돌릴 때는 행렬을 뒤집기만 하면 된다.** 이런 회전 행렬은 가로줄과 세로줄을 바꾸는 것만으로 역방향 변환이 된다(전치 = 역행렬). 역행렬을 따로 계산할 필요가 없어서 빠르고, 계산 오차도 생기지 않는다. 궤적을 화면에 그릴 때 이 성질을 쓴다.

### t=0 확인값

| 표적 | 자세 | ECEF 속도 [m/s] | 크기 |
|---|---|---|---|
| 대함 (32.125°N, 126.03°E, 30 m/s) | Yaw 270° (서쪽) | (24.2613, 17.6463, 0.0000) | 30.000000 |
| 대공 (32.12°N, 126.0°E, 200 m/s) | Yaw 180° (남쪽) | (−62.5044, 86.0299, −169.3873) | 200.000000 |

대공 표적의 z 성분이 음수인 것은 고도가 내려가서가 아니라, 남쪽으로 가면 북극 쪽 성분이 줄기 때문이다.

## 기동이 궤적을 휘게 하는 원리

기동은 **위치를 직접 건드리지 않는다.** 자세각을 돌리면 다음 스텝의 속도 방향이 바뀌고, 그 결과로 궤적이 휜다.

### 몇 G 로 돌면 얼마나 빨리 도는가

원운동을 할 때 안쪽으로 당기는 가속도는 `속력 × 각속도` 다. 명세의 Gravity Value 는 이 가속도를 중력의 몇 배로 줬는지를 뜻하므로

```
속력 × 각속도 = n × 중력가속도
      각속도 ω = n × 9.80665 / 속력
```

여기서 두 가지가 바로 나온다.

```
선회 반경  R = 속력 ÷ 각속도 = 속력² / (n × 9.80665)
선회 주기  T = 한 바퀴 도는 시간 = 2π × 속력 / (n × 9.80665)
```

| 속력 | G | 각속도 | 선회 반경 | 한 바퀴 | 0.1초에 도는 각도 |
|---|---|---|---|---|---|
| 30 m/s | 1G | 18.7°/s | 92 m | 19.2초 | 1.87° |
| 30 m/s | 2G | 37.5°/s | 46 m | 9.6초 | 3.75° |
| 200 m/s | 1G | 2.8°/s | 4,079 m | 128.1초 | 0.28° |
| 200 m/s | 2G | 5.6°/s | 2,039 m | 64.1초 | 0.56° |

같은 G 라도 느린 표적이 훨씬 급하게 돈다. 30 m/s 배는 2G 로 반경 46 m 안에서 도는데, 200 m/s 비행기는 같은 2G 로 2 km 짜리 원을 그린다. 익숙한 감각과 반대라 처음에는 헷갈린다.

이 각속도를 TurnType 이 지정한 축에 넣는다.

```c
omega = (gravityValue * G_FORCE) / headingSpeed;

switch (enTurnType) {
case TGT_TURN_NONE:                            break;   // 안 돈다
case TGT_TURN_ROLL:   st_Rate->roll  = omega;  break;
case TGT_TURN_YAW:    st_Rate->yaw   = omega;  break;
case TGT_TURN_PITCH:  st_Rate->pitch = omega;  break;
}
```

속력이 분모에 있으므로 0이면 안 된다. 그래서 표적 속력은 0보다 커야 한다는 검사를 미리 건다. 플랫폼은 정지(0 m/s)가 허용되는데, 플랫폼은 기동이 없어서 이 나눗셈을 아예 지나가지 않기 때문이다.

## 한 스텝 나아가는 방법 — 왜 중점법인가

가장 단순한 방법은 **스텝 시작 시점의 속도로 0.1초 동안 이동**시키는 것이다. 문제는 도는 중이라면 0.1초 사이에 방향이 이미 바뀌었다는 점이다. 시작 방향으로만 직진하면 원의 바깥으로 계속 밀려난다.

그래서 **스텝 한가운데(0.05초 지점)의 방향으로 0.1초를 이동**시킨다. 앞쪽 절반에서 덜 도는 오차와 뒤쪽 절반에서 더 도는 오차가 서로 상쇄된다.

```
1. 0.05초 뒤의 자세를 구한다          att_mid = 현재자세 + 각속도 × 0.05
2. 그 자세로 속도를 만든다             V_mid   = (body → NED → ECEF 변환)
3. 그 속도로 0.1초 이동한다            P_new   = P + V_mid × 0.1
4. 새 ECEF 위치를 위경고도로 바꾼다
5. 자세는 0.1초 끝까지 돌려둔다        att_new = 현재자세 + 각속도 × 0.1
6. 최종 자세·위치로 속도를 다시 만든다 (출력용)
```

| 방식 | 200 m/s, 1G 로 선회할 때 반경 |
|---|---|
| 시작 방향으로 직진 | 이론값보다 약 0.72 % (≈ 30 m) **크게** 나온다 |
| 중점법 | 상쇄되어 이론값에 붙는다 |

추가 비용은 속도를 한 번 더 만드는 것뿐이라, 더 복잡한 방법(RK4)까지 갈 필요가 없다.

**알려진 한계** — 자세를 roll·pitch·yaw 로 직접 다루기 때문에, pitch 가 ±90°(수직 상승·하강) 근처가 되면 yaw 축이 진행 방향과 겹쳐서 yaw 기동이 궤적을 바꾸지 못한다. 짐벌락이라고 부르는 현상이다. 쿼터니언을 쓰면 없어지지만, 명세가 자세를 roll·pitch·yaw 로 규정했으므로 표현을 유지하고 한계를 기록해 두는 쪽을 택했다.

# 기동 시간 구간 — 왜 이걸 정해야 했나

명세가 답을 주지 않은 세 번째 항목이다. **기동이 하나뿐이면 이 이야기는 전혀 필요 없다.** 표적마다 기동을 최대 30개까지 넣을 수 있게 만들었기 때문에 생기는 문제다.

## 문제 1 — 기동 두 개를 이어 붙였을 때

```
기동 A :  0초 ~ 20초   Yaw 2G
기동 B : 20초 ~ 40초   Pitch 1G
```

**20.0초 정각은 누구 것인가?** 양쪽 다 자기 구간이라고 한다. 코드는 배열을 앞에서부터 훑으니 A 를 집고, B 는 시작 한 스텝을 잃는다.

한 스텝이 별것 아닌 것 같지만 계산해 보면 그렇지 않다. 200 m/s 표적이 1G 로 돌면 0.1초에 0.281° 를 돈다. 그 0.281° 가 빠진 채로 남은 30초를 날면 **약 29 m** 가 어긋난다.

그래서 **끝 시각은 포함하지 않는다**고 정했다.

```
20초 정각은 A 가 아니라 B 의 것
```

"10시부터 11시까지 회의"라고 하면 11시 정각은 회의가 끝난 시각인 것과 같다. 이렇게 하면 `0~20`, `20~40`, `40~60` 을 **빈틈도 겹침도 없이** 이어 붙일 수 있다. 어려운 개념이 아니라, 정해두지 않으면 경계에서 한 스텝이 새는 **약속**이다.

## 문제 2 — 기동 두 개가 진짜로 겹칠 때

```
기동 A :  0초 ~ 20초   Yaw 2G
기동 B : 10초 ~ 30초   Pitch 1G
```

10~20초 구간에는 **답이 없다.** 둘 다 적용해야 하나, 하나만 해야 하나, 한다면 어느 쪽인가. 명세 어디에도 없다.

코드가 조용히 아무렇게나 처리하게 두면(예: 앞의 것 우선), 그 규칙은 내가 만든 것이지 물리적 근거가 없다. 그래서 **실행 전에 오류로 반려**한다.

```c
// 겹치지 않으려면 한쪽이 다른 쪽보다 완전히 앞서야 한다.
// 그 조건이 깨지면 겹친 것이다.
if ((A.startTime < B.endTime) && (B.startTime < A.endTime))  ->  TGT_ERR_MANEUVER_OVERLAP
```

합성을 허용하는 설계도 물론 가능하다. 다만 그러려면 합성 규칙을 내가 새로 정의해야 하고, 그건 과제 명세에 없는 동작이 된다. **모르는 입력을 추측해서 처리하는 것보다 거부하는 편이 정직하다**고 봤다.
